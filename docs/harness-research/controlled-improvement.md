# 受控改进与任务交付

目标是用最少必要的用户投入，得到可运行、可核对效果的业务智能体。管理助手先查当前对象和已存在信息，再确定最小任务；已获授权的范围内连续执行，只对会改变业务目标、输入、验收或外部权限的缺口提问。

## 从业务结果开始

用实际输入和可观察产物表达成功。例如“对指定设备逐台统计并提供可下载报告”比“具备巡检能力”更可验证。核对目标、固定父版、所需工具与已有 Case，优先复用真实装载的 DSH 能力、插件、MCP 和技能。只生成角色说明、复制文件未绑定 Preset，或仅登记工具名称，均不证明业务能力就绪。

研究假设写清改什么、为什么、如何被证伪、不能回归什么和何时停止。信息足够后提出可执行方案，不将用户带入固定长问卷，也不要求每个阶段重复确认。对现有业务 Harness 的语义修改创建独立 Experiment；只整理文档或历史证据按实际影响检查，不因此制造新研究版本。

沿失败事实查共同原因：先确认目标与实际来源，再看输入、真实动作、工具结果和产物，最后检查生成与消费链。用成功反例检验解释，区分模型判断、缺数据、工具失败、评判错误和平台缺陷。只修共同原因直接影响的资产，不顺手改其他 Prompt、配置或模型。

## 有限修复与恢复

任务型交付在计划中固定业务 Case、回归、工具、产物、允许动作和预算。初测保留完整 Run；每轮“分析→修改→复测”先预留额度，失败轮也计数，最多三轮。修复不能改原 Case 的预期、把失败回答变成答案、悄悄缩小设备集合或删除失败证据。

暂停恢复前读已有任务、job 和实例状态；额度和对象保持连续。回执未知的外部动作先查实际状态，不盲目重发。发生回归时仅回退本任务修改且摘要仍吻合的文件；检测到用户并行修改就停止覆盖并说明冲突。没有固定可恢复父版的首次失败 Candidate 保持未交付，不影响已有版本。

任务预算分别核对管理助手、业务执行、评审和交付探针的实际消耗。调用未知或只采集到下界时明确限制，不用调用次数推算账单，也不声称未受执行器限制的外部消耗已经硬封顶。

## 交付与结论

评测容器和交付实例各有自己的 HOME 与 Session。交付时验证实际实例的来源和新业务调用，核对报告可读取、设备完整性、关键工具结果与下载内容；不能把评测临时链接拼成实例产物地址。HTTP 成功、模型自报完成和同模型评分都不能替代业务验真。

保存与加载是不同事实：修改必须进入目标 Candidate，生成物要对应源码，实例实际装载需新 Session 或新进程核对。沿用业务智能体的标准 Runtime 镜像；易变 Harness 通过现有装载方式生效，不为每次研究创建派生镜像。

按证据记录 adopt、continue、reject 或 inconclusive。失败、没有收益和证据不足都可以结束一轮有价值的研究；不能为了“完成”放松口径。业务 Mock 明确标出替代的外部边界。真实训练缺算力、依赖或数据时如实停在预检，不编造训练指标。

研究流程服务当前问题，不预建生产审批、固定 Case 数、额外流程台账或空产物。需要 Research Release 时先说明复现目标与当前工具缺口；当前管理平台没有自动创建发布入口。

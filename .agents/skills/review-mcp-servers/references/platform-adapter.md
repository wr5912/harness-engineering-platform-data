# 平台取证与 OpenAPI 来源

审查当前工作区的实际对象。连接配置从 `platform_mcp` 的 `configuration` 读取；`serverId` 使用回执中的连接 ID，保留 `revision`。不读取凭据文件，不另存可编辑的连接、工具目录或 OpenAPI 副本。取证快照只说明对应时间和版本。

## 按来源取证

| 来源 | 读取路径与归因 |
|---|---|
| 原生 MCP 连接 | `test {serverId}` 取工具定义，按需 `resources {serverId}`、`resourceTemplates {serverId}`。描述和 schema 来自实际上游发现结果；原生 MCP 服务也可能在内部转换 OpenAPI，不能仅凭传输方式排除这种来源。 |
| 连接直接配置 `specUrl` | 对照配置指向的 OpenAPI 原文、平台转换目录及目标 DSH 的实际发现结果。使用已可用的原生只读能力读取公开规范；受保护且公开接口未提供原文时，说明缺少该版本规范，不能读取凭据或改配置绕过。 |
| 上游服务管理的 OpenAPI 来源 | 只有目标确实提供来源管理接口时，使用 `sources/list {serverId}`；以真实 `sourceId` 读取 `sources/components {serverId,sourceId}`，必要时读取 `sources/logs`。不要把这些接口当成所有 MCP 服务都有的标准协议；组件结果也不必等于原始规范。 |
| 平台分组 | 先读取 `configuration.groups` 的成员及所选工具、资源和模板，再与目标 DSH 实际发现对照。平台 v2 公开原始工具名或转换后的 `operationId`；DSH 以完整分组 ID 添加一次命名空间。来源身份从配置及返回元数据定位，不拆解公开名称推断成员服务。 |
| 已发布编排 | `list` 固定具体发布版本，必要时 `compositionSource` 只读核对该版本源码和定义。描述归编排本身维护，不把子步骤的 OpenAPI 描述当作整个编排的行为承诺。 |

动作参数先用 `platform_mcp` 的 `describe` 读取；工具实际调用形式为 `action` 加 `input`。`test` 只证明发现结果，不证明业务调用成功。接口没有提供的协议版本、分页、Prompt 或原始报文标为未知或待补证，不虚构管理动作。已有足够证据时不重复发现全部连接。

## OpenAPI 描述如何影响模型

以下是本次接入核对的实现定位，复核时以目标运行版本源码和实际目录为准，不把工作树规则冒充旧实例已加载的规则：

- 程序根 `plugins/mcp-manager/openapi.ts` 的 `loadOpenApi`、`operationSchema`、`schemaOf` 是平台 MCP 管理的转换实现，`platform/plugin/build.mjs` 复用它；`platform/plugin/src/mcp/openapi.ts` 另有本地连接转换路径，需按实际调用链区分。
- 当前工具、资源及模板的主要说明取 `operation.summary || operation.description || "METHOD /path"`；两者同时存在时不会自动拼接。`summary` 简短而 `description` 含关键前提或副作用时，必须核对这些信息是否在最终定义中缺失。不能只建议修改一个当前不会被消费的字段。
- 名称优先取 `operationId`，缺失时从 method 和 path 派生，并清洗不支持的字符。对照原始 ID、HTTP method/path 和最终名称；清洗后的冲突与分组内重名不能靠再叠加成员前缀掩盖，应报告实际冲突与可用整改位置。
- 主转换器将参数 `schema` 映射至 `inputSchema.properties`，参数自身的 `description` 优先于 schema 的说明；JSON 请求体映射到 `body`，字段说明来自对应 schema。`requestBody.description`、`responses` 说明不自动成为工具描述或 `outputSchema`。Schema 只转换当前支持的子集，不能将源规范中的约束或默认值一概视为运行时已校验或已应用。
- 符合实现条件的 GET 会成为资源或资源模板，带 query 的部分 GET 同时保留工具；业务工具目录还可能有不同投影。只看 `tools` 不能断定接口缺失，也不能据 GET 或只读注解直接证明无副作用。
- 分组可将所选资源或模板再包装为工具，在源说明后附加“读取资源：URI/模板”。这属于适配器说明，不是上游规范原文，也不自动构成业务 SOP。按真实元数据和调用行为区分。

典型检查：同一操作的 `summary` 是“创建巡检”，`description` 另写“仅受理，返回 requestId；查询结果才表示完成”。若最终定义仅有“创建巡检”，记录丢失的语义及对调用的影响，定位到实际转换选择；不能把“规范中已写”当成模型已经看见，也不能仅凭说明缺失断言服务端实际违规。

## 最小整改与生效核对

| 证据 | 整改位置与复验 |
|---|---|
| 源规范缺失、错误或夹带调用方流程 | 建议修改原服务的 OpenAPI 维护源及其生成器；工具所需前提、结果和副作用保留，业务 SOP 归对应 Skill。平台不维护第二份同义描述；第三方服务只给出可复验建议，未经授权不修改其仓库。 |
| 原文正确，转换后丢失或改义 | 报告平台转换器或上游来源转换服务的具体差异及调用链，交对应维护方修共同转换入口；不能直接编辑生成目录或以 Skill 补写所有工具契约。 |
| 转换正确，分组或 DSH 发现仍旧 | 核对来源版本、选择配置、分组身份及实际装载目录，按原生刷新、重新发现或新 Session 机制验证；只在确有必要且获授权时使用 `sources/refresh` 或修改配置。刷新失败不自动升级为业务调用、发布或重启。 |
| 定义准确，模型仍选错工具或误解结果 | 对照相近工具和调用轨迹，分别评估描述区分度、参数来源与 Skill 编排。固定模型、候选目录和独立 Session 比较，缺少行为证据时只提出待验证假设。 |

整改建议至少定位到 `serverId`、实际来源版本或摘要、`operationId`/HTTP method/path、最终工具名及具体字段；未知项注明未知。将规范原文、源目录、分组结果及模型可见定义逐层引用，不把上游工具同名当成同一对象。

只审描述时做到静态证据闭环即可；需证明实际选择或副作用时，从现有验证参考中选必要用例。优先检查：短 summary 覆盖长 description、参数说明与 schema 不一致、GET 资源在分组中出现、上游刷新失败，以及“只审查”请求不产生配置或业务写入。没有实际执行的行为标为待验证；不要求调用全部工具或探测所有服务。

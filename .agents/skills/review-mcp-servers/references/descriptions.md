# 描述与工作流边界

给每条发现标明下表中的依据。先对照 handler、上游文档、返回样本与调用轨迹，再判断文字是否准确。以下 D 规则用于质量审查；协议字段的必填属性按 P 规则判定。

平台接入先按[平台取证与 OpenAPI 来源](platform-adapter.md)核对规范原文、转换目录、分组和 DSH 实际发现。D 规则不自动成为项目发布门禁；不能把转换丢失的说明归咎于源服务，也不能仅因源规范已有说明就认定模型已看见。

| ID / 依据 | 生效条件 | 核验与失败判据 |
|---|---|---|
| D01 审查质量规则 | 目录向用户或模型发布工具、资源、资源模板或提示模板 | 从实际提供的目录检查各条目。描述应给出足以识别用途的信息，只有名称复述、占位符或空文本时指出具体缺失及调用影响；协议允许省略上述 description，不能单凭缺失判为协议失败或阻断。 |
| D02 审查质量规则 | 工具可调用 | 对照单次 handler 和真实结果。写清动作与对象、影响调用选择的前提、结果含义和重要副作用。能分清查询/探测、预览/提交、已受理/已完成。简单工具一句话即可。与实际行为矛盾即失败。 |
| D03 审查质量规则 | 工具描述含操作步骤、关联工具或场景流程 | 逐句使用下方归属表。发现工具把调用者引向与本次调用无关的必做步骤，或把调用方 SOP 宣称为自身能力，即失败。保留真实参数依赖和结果使用条件。引用原句及实现证据，给出保留、迁移、强制校验的具体改写。 |
| D04 审查质量规则／工程实践 | 参数或返回值有歧义 | 检查稳定 ID、单位、时间与时区、枚举、默认值、分页、无数据与失败。只检查影响该接口的项。能机器校验的限制与实现相符；文字解释值来源及条件必填。已证实语义冲突或导致错填时阻断，单纯可读性建议列改进。 |
| D05 工程实践 | 两个工具候选接近，或新增工具与既有工具重叠 | 把目录并列，用同一用户问法检验差异。根据真实差异补上适用条件或结果边界。单纯词语相近不足以认定重复。根据对照用例判断是否合并工具，或拆开不同权限的动作。 |
| D06 审查质量规则／工程实践 | Resource 或 ResourceTemplate | 描述数据含义、范围及有业务意义的时间口径；模板还应说明变量来源和合法例子。拿返回值里的 ID 或 URI 实际展开并读取，对照 MIME 和内容。在只读证据接口读出其他对象、主动触发业务写入，或文案虚称“实时”，按实质影响判定。 |
| D07 审查质量规则／工程实践 | Prompt 或 server instructions | 对照 prompts/list 与 prompts/get 的实参和消息。用户能判断何时选模板、提供什么、获得什么。核对模板渲染和参数边界。服务全局说明保留简短共用约定，长流程归对应 Skill；宿主可能不将 instructions 交给模型。任何审批与授权均需核查执行点。 |
| D08 工程实践 | 聚合多服务器、多宿主或改名 | 比较服务内 name、宿主实际发现名称与 Skill 引用，检验重复名和失效引用。平台 v2 分组保留原始工具名或转换后的 operationId，DSH 以完整分组 ID 添加一次命名空间；以实际发现的 `mcp__<group-id>__<tool-name>` 为准，不猜名称或叠加成员前缀。协议命名要求查 P 规则。用调用失败或目标错配证实兼容影响。 |

## 逐句归属

| 这句话决定什么 | 维护位置 | 评审操作 |
|---|---|---|
| 本次调用是否适用、接收什么、真实改变什么、返回什么 | 工具 description、字段说明、schema | 保留。工具内部为一个业务结果编排多次 API 是合理实现。说明外部可观察的动作和副作用。 |
| 某个参数从哪里获得，什么状态才接受，某个返回值之后怎样查询 | 对应参数或工具说明 | 保留必要说明；已有 ID 可直接用时，删掉“每次先查一次”。状态、权限等必要条件同时在服务端落实。 |
| 服务内多个能力都遵守的一条稳定约定 | server instructions | 集中维护。单工具独立使用所需的重要前提和副作用仍须可见。 |
| 调用者围绕某个业务目标应如何编排多个工具、遇到什么证据分支、怎样审批流转、如何出报告 | 对应 Skill 正文或业务剧本 | 迁出工具描述并定位唯一维护位置。宿主按需加载 Skill；需要确定性执行的步骤用代码或编排引擎实现。 |
| 越权必拒、预览无写入、审批绑定对象和方案、重试无重复写入 | 实际执行端的校验、状态机或幂等机制 | 在工具中说明外部承诺，在实现和负向测试中取证。 |

## 评审校准

- **保留参数依赖**。更新文件时，旧版本标识必须来自同一目标分支和路径。写明如何取得，能避免错误覆盖；GitHub 官方工具的 blob SHA 即为实例。[GitHub MCP Server](https://github.com/github/github-mcp-server)
- **迁出业务流程**。工具“读最近一次资产观测”的实现只查询数据库。若描述还要求模型“探测、下工单、生成日报”，保留观测时间、数据来源和缺失语义，将后三步归入巡检 Skill。单独询问上次观测时间时，预期网络探测和写入均为零。
- **保留复合工具**。若一次提交由服务端校验库存、预留名额并创建订单，描述要披露创建和占用行为。对照代码和事务结果，避免见到多动词就误报。
- **辨清异步结果**。“返回作业 ID 表示受理；查询作业可取得执行结果”是工具契约。“作业完成后分析攻击链并向所有人发送总结”由业务流程决定。

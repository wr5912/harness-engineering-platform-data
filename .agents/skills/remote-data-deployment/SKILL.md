# 远端数据工作区更新

将用户指定的数据交付到指定安装，并取得保存与装载回执。复用程序根的 `platform/dsh-deploy`；命令合同先读 `<program_root>/docs/platform-design/23_离线一键打包与安装.md` 和工具 `--help`。本技能维护办理方法，参数与实现以该工具为准；命令示例见 [commands.md](references/commands.md)。

## 先固定来源与目标

1. 从受信任上下文取得本地 `program_root`、`asset_root`；核对用户授权的主机、更新内容和保留对象。232、52、170 是环境简称，实际使用明确的 SSH 地址。只有咨询或预检授权时不应用更新；本次授权不延续到后续远端同步。
2. 只读核对目标平台进程、安装清单、实际程序根与数据根、平台入口、架构及完整／最小数据模式。只读取必要的非敏感字段，不输出环境文件、配置或凭据全文。默认程序目录是 `~/work/harness-engineering-platform-data`，数据目录是 `~/harness-engineering-platform-data`；已有安装以现场定位为准，历史验收目录不能替代当前路径。SSH 参数使用远端绝对路径，不把本地 `~` 展开成远端目录。
3. 核对本地与目标的程序提交、数据来源提交、工作树和暂存区；整库更新要求两仓暂存区为空，不能替用户清空。“最新”需要可核验的来源，未核对远端分支时只称本地 HEAD。最小安装分别记录其派生提交与完整来源提交，不能按两个 HEAD 不同判为落后。保留并行修改，不自动提交、推送或重置工作树。
4. 核对受影响会话、在途任务与业务实例，记下必须保留的实例身份、HOME、会话、端口和访问配置。数据与 Session、缓存、附件、实例 HOME 分开；不把运行目录当作资产同步，不复制整个 DSH HOME。

## 选择最小更新范围

| 本次目标 | 工具路径与边界 |
|---|---|
| 更新管理助手 `AGENTS.md`、根级 Skill、参考资料，或同步完整数据仓库 | 已安装双仓使用 `update`，来源是两仓已提交 HEAD，未提交文件不在交付范围。 |
| 更新一个已安装业务实例所用的固定 Experiment 资产 | 使用 `agent-update`，交付清单中的实际已保存文件，可包含未提交修改；先核对 Agent、完整 Experiment ID、实例及远端前置摘要。 |
| 更新现场配置、工作区身份或凭据 | 整库 `update` 保留 `config/`、`workspace.json` 与运行状态，不能据此宣称配置已同步。按真实可用的平台配置入口单独办理，不覆盖这些目录。 |
| 目标尚未安装，或明确要求迁移目录 | 按程序文档使用 `pack`／安装器或 `relocate`；不将普通数据更新扩展成全量重装或目录迁移。 |

`update` 同时处理程序和数据，没有 `--data-only`。用户只要求数据更新时，选择已准备、程序 HEAD 与目标安装一致的源码工作区，通过 `--program-root` 指定，并确认预检不引入程序或依赖变化；无法做到时报告工具缺口，交由研发整改后继续，不顺带升级程序，也不虚构参数。未提交的管理技能不能借 `agent-update` 交付；需要来源提交或工具能力支持时明确说明，不自行提交。

最小安装始终带 `--minimal-data`：只刷新管理身份、根级 Skill、资料与来源说明，保留现场业务资产、配置、会话和最小仓库历史。170 按用户既定要求默认保持最小模式，除非用户明确更改；232、52 等目标按现场安装模式和本次授权判断，不仅凭 IP 推断。向最小环境交付某个业务版本是另一个明确目标，不导入全部研究历史。

## 预检、应用与恢复

普通管理会话使用实际可用的原生 `bash` 与长任务工具调用公开 CLI；没有执行能力时交付准确阻塞，不伪造平台动作。固定研究、抽样或 `plan_only` 上下文保持原限制，不通过新会话、换身份或清空上下文绕过。

1. 使用选定工具执行 `--dry-run`，核对目标身份、来源、范围、完整／最小模式、冲突和保留项。出现授权外变更时，缩小工具可支持的来源或报告定向能力缺口，不扩大同步范围。整库预检会构建已提交快照并使用远端临时传输目录，但不修改目标安装文件；不把它描述为完全没有远端写入。
2. 预检与既有授权一致后用同一组参数去掉 `--dry-run` 应用，不再索取重复确认。文件或来源变化后重新预检。耗时操作保留原生任务 ID，使用 `job_output`、`job_list` 跟进；不因暂时没有输出重复启动更新。
3. 默认只传增量，不传全量仓库、镜像、依赖目录或运行状态。仅在依赖合同确有变化且属于本次授权时使用工具的 `--install-deps`；核对目标架构，不能把 AMD64 原生依赖直接用于 ARM64。目标全局缺少 Node、Git 不等于必须在线安装，先核对安装器自带工具。
4. 失败保留命令的非敏感参数、阶段、错误码、来源和回执位置。摘要冲突先查并行修改；连接中断或结果未知先查回执与文件状态，再决定恢复或重试。不盲目覆盖、清锁、重放外部写入或批量杀进程。确为本工具离线准备卡住时，核对归属后按合同使用 `--cancel-prepare`。
5. 工具失败或不适配时，把必要修复交回程序仓库的打包部署工具并验证，再通过同一工具继续。管理助手不因部署缺陷切换为平台研发，不用临时 `scp`、`rsync`、Git 检出／重置或一次性部署脚本替代。备份、回滚、保留 inode、跨架构依赖与大数据传输交给维护工具，不在 Skill 中复制一套实现。

## 核对实际生效

- 读取工具回执、目标数据来源与受影响文件摘要，区分已保存、待装载、已装载和失败。整库与定向更新的回执分别位于程序根 `.local/deploy-updates/`、`.local/deploy-agent-updates/`；`activation: pending` 不能报告运行中已生效，`recovery-required` 不能报告已回滚完成。
- 管理原则与 Skill 先核对 DSH 原生发现及新建／恢复会话的实际加载；文件存在不证明当前会话已更新。平台先用原生热加载、配置重载或新 Session；确需重新装载进程时才使用合同中的 `--start`，先核对空闲和影响，不仅因为文件更新就重启。
- 业务资产通过既有实例生命周期核对差异和装载回执；必要时仅重载或重启目标实例，保留 HOME、会话、端口、模型与网关设置，并验证一个与改动直接相关的行为。停止中的无关实例不启动，其他业务容器不重启。
- 在目标安装上按工具合同运行 `verify`，需要在线核对时提供真实平台入口。按本次范围核对管理助手工作区、技能发现或目标实例；HTTP 可达、静态校验与业务效果分别说明。外部 MCP 不可用时保留具体业务限制，不把它误报为部署失败或阻止其他正常交互。

交付说明只保留必要事实：目标与实际目录、来源提交或资产摘要、更新模式与范围、工具回执及恢复位置、装载证据、未完成项。经验涉及公共缺陷时沉淀到维护工具与唯一合同；不另建主机目录台账、凭据副本或第二套部署脚本。

# 评测用例审查与优化

版本：V0.5
作者：luopeng
日期：2026-11-05

## 默认交付

交付可直接使用的用例，结构固定为：

**用例标题 + 评估档位（可选）+ 用户输入 + 预期**

使用 [用例模板](assets/case-template.md)。模板默认省略可选评估档位；原用例有 fast 时保留，新建用例按测试计划决定。

将需求核对、证据检查和质量自检用于写作过程。默认只输出用例正文，不附“基本信息”、步骤表、断言编号、追溯矩阵、设计状态、执行结果、JSON 或审查报告。用户明确要求额外交付时再按任务补充。

简单预期用一段话；有先后关系或多个主要检查点时，用普通编号拆分。每步写清动作与可观察结果即可，不要求固定步数，也不要求每步套相同子字段。

## 工作步骤

### 1. 读原材料，确认要验收的行为

先读[评测口径与输入](../../../docs/harness-research/evaluation-and-evidence.md#口径与输入)、原用例及用例总则，再按需查业务需求、工具合同和相关失败记录。默认保留既有 ID、评估档位、真实用户输入及有效验收要求；只有用户明确授权的非语义编号整改可按[用例编号与授权改号](references/platform-adapter.md#用例编号与授权改号)调整 ID。名称准确表达业务目标，移除实现路线限制时同步修正标题。

用材料确定用户要完成的任务，以及什么结果算完成。现有实现和历史回答可用于调查，不能自动当成正确答案。材料中的历史设备数、示例 ID 等动态值不写死为新用例答案。

只补会影响本条判定的信息。未确认的阈值、字段优先级和新产品承诺不自行添加；实质性缺口用一句话说明，不要求补齐一套资料表。

### 场景覆盖：从用户当前知道什么开始

审查整份用例或某个业务域时，先检查入口是否只剩“用户已给齐对象、ID 和参数”。按实际需求覆盖以下交互，不要求每个业务机械复制一套用例：

- 用户不知道有哪些对象或问题，先咨询能力、查询候选或了解异常；查询必须有真实来源、范围、时间及分页边界，咨询本身不授权执行。
- 用户从结果中选“第二台”“刚才那个事件”，助手沿同一会话的真实身份继续定位、分析；候选歧义才询问，不能取搜索首条、猜 ID，或要求用户重新提供已经取得的信息。
- 用户根据分析结果要求预览、草稿或执行，按本轮结束位置完成真实任务；同时保留参数完整时直接办理的路径，不能为覆盖发现阶段强制每次重查。
- 与当前任务有关的空结果、查询失败、部分结果、对象变化、改选和取消有可判定处理；查询失败不等于没有问题，历史候选不当作当前事实，取消或只读请求不得偷偷续办写入。

检查跨域承接是否保留原结果、目标及用户授权，例如巡检后排障、事件研判后处置、故障定位后策略草稿。用真实多轮输入覆盖必要转折；只有单独的目录查询和单独的执行用例，不能证明衔接已覆盖。用例内容只维护在 Agent 的 evaluation.md，方案和技能引用即可。

### 2. 写标题、档位和真实输入

- 标题只写一个符合[统一编号规则](references/platform-adapter.md#用例编号与授权改号)的用例 ID 与业务名称，不另附来源编号或编号别名；不得沿用不合规的旧编号形式。
- 原用例有“**评估档位：** `fast`”时，原样放在标题后的第一个非空行；原来没有则保持省略。只有明确调整快速评测范围时才改动标记。
- 新建用例按测试计划决定是否加 fast；不写 full 标记。fast 只标识该用例纳入快速集合，不降低预期。
- 用户输入保留真实对话。单轮输入放在“**用户输入**”下，多轮按真实轮次编号；不要把 Agent 内部步骤改成用户必须逐条下达的指令。

### 3. 写预期，按需拆主要流程

围绕业务闭环写“做什么、应得到什么结果”。有必要时按查询、执行、等待、交付等主要检查点分步，合并能一起理解和核对的内容。

用可观察的对象、状态、字段关系和产物说明业务处理过程及结果模式，展开“正确、准确、完整、合理”等空泛词。必要的工具名称、参数和顺序以已确认 API 合同为准，按当前目录映射实际入口，允许非关键实现和自然表达差异。

经授权迁移业务合同时，移除失效的本地台账、私有状态或固定确认界面要求，保留原业务目标、明确的用户限制和正向完成证据。接口尚不支持目标时记为未通过或证据不足，不能改成“说明缺口即通过”；不改写历史 Run 的冻结口径。

把“不应、不能、不得”等约束就近写成对应步骤的注释；简单用例可放在段落末尾。影响通过与否的约束仍属于预期，注释只是排版方式，不是降低要求。例如：

- 主流程：使用本轮启动返回的 runId 查询，直到报告就绪。
- 注：后续只跟踪这次运行，不重复启动；运行中、工具失败或报告未就绪时不声称完成。

已有异常分支条件直接写清，如“若结果为 PARTIAL，说明证据缺口”。只有任务要求覆盖异常场景，或独立条件确实需要另测时，才另写用例；不要给每条正常用例自动附场景矩阵。

### 4. 对照检查，交付正文

交付前核对：

- 整份当前用例清单是否逐条通过[统一编号规则](references/platform-adapter.md#用例编号与授权改号)检查，含编号格式、唯一性及标题无第二套编号？
- 原要求是否保留，fast 标记及真实对话是否保留？
- 是否按[场景覆盖](#场景覆盖从用户当前知道什么开始)检查了用户从未知对象开始的多轮任务及直接办理路径，而不只核对已知 ID 的单条用例？
- 每项主要预期能否用本轮回复、工具回执、状态或产物判断？
- 必要产物、关键约束和已规定的失败分支是否遗漏？
- 是否把历史样例当成固定答案，或增加了无来源的门槛？
- 是否违反共用口径，把 KEV 等实现路线、MCP 运行时 ID、私有字段或特定环境写成业务标准？稳定接口名称与字段是否有实际合同依据？
- 是否有可删的字段、步骤、重复说明或只为展示严谨而增加的材料？

简化表述，不删除必要要求。重要事实和产物缺失，不能靠回答流畅抵消；缺少必要证据，不能断言验收通过。

默认交付用例正文。审查任务按用户问题简要指出问题，再给必要的改写。实际保存、运行和结果记录沿用现有平台能力，不在用例里另建一套管理流程。

## 按需参考

- 写入 Harness 的 evaluation.md 前读 [平台格式](references/platform-adapter.md)，保证原生解析兼容。仅排序按该文的场景内排序合同提交完整 Case ID 顺序与摘要，不生成整份文件。
- 参考 [U-INS-001 示例](assets/u-ins-001.platform.md) 掌握粒度：主要流程加必要注释。
- 用户追问专家方法、原始材料、工具或外部标准时读 [方法依据](references/sources-and-methods.md)。这些是设计参考，不是每条用例的必填字段。

## 用例写入交接

接收 agent-maintenance 固定的 Agent、场景、用户授权的增改/改号或排序范围及当前摘要；按 [平台适配合同](references/platform-adapter.md) 校验编号、预览并写入，回读完整标题与顺序后返回原任务。仅排序提交 ID 顺序，不重写正文；未知写入先查，不重复提交。

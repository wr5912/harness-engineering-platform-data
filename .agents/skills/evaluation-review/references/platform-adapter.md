# Harness 用例格式

格式依据 2026-11-02 已核验的仓库版本；编号及改号操作按办理时核对的平台合同执行。后续涉及平台行为变化时重新核对。

## 四部分结构

内容口径遵循[评测口径与输入](../../../../docs/harness-research/evaluation-and-evidence.md#口径与输入)，本文件只维护格式及平台适配。

1. 用例标题：按[用例编号与授权改号](#用例编号与授权改号)写一个合法编号与业务名称，不附加其他用例编号。
2. 评估档位可选：只有纳入快速集合时写“**评估档位：** `fast`”，放在标题后第一个非空行。改写默认保留原值；未标记时省略，不写 full。
3. 用户输入：单轮用“**用户输入**”，多轮用“**用户输入 1**”“**用户输入 2**”连续编号；每个非空输入行以 > 开头。
4. 预期：末尾只出现一次“**预期**”。简单内容写一段，必要时用普通编号列主要步骤，约束就近写“注：”。

预期仍是一个文本字段。页面保留换行展示，普通编号适合直接阅读；无须改成步骤表。原生解析不代表自动执行或逐步评分。

## 用例编号与授权改号

本节是用例编号规则的唯一详细维护位置，其他入口只引用本节。

1. **唯一合法格式。** 当前用例编号严格限定为 `U-场景英文缩写-三位数字`，完整匹配 `^U-[A-Z]+-[0-9]{3}$`。场景缩写只能是一段大写英文字母，不含数字、空格或连字符；序号为 `001`～`999`，不使用 `000`、不足三位或超过三位的数字，也不以 `FAST`、`MENTION`、`RULE-REAL` 等文字替代数字后缀。完整标题只能是 `#### 合法用例编号 业务名称`：仅出现一个用例编号，业务名称前后均不得追加第二套编号、来源编号或编号别名，例如 `IQ-BND-001`、`IQ-TPL-004`。真实用户输入和业务对象标识不因编号整改改写。
2. **沿用合规场景缩写并递增。** 用例归属由当前文件的二级场景标题确定，同一场景统一沿用已有的合规英文缩写；从该缩写当前最大数值序号之后递增，不回填空号。完整用例 ID 必须在当前 Agent 的 evaluation.md 全文件唯一。达到 `999` 时停止并说明编号空间已用尽，不自行扩为四位或另造缩写规避。
3. **明确合规新缩写。** 所属场景没有既有合规缩写时，先明确有业务含义的单段英文缩写；已有多段缩写在授权整改中统一为合规单段缩写。不使用 `NEW`、`XXX` 等占位缩写，不因草稿默认值改变场景归属，也不把旧编号形式当作继续新增违规编号的例外。
4. **按场景选择新编号。** 新建先调用 `cases/create-context`，读取当前摘要、场景及 `case_id_suggestions`，从所选场景的建议选择编号；切换场景后重新选择对应建议。建议值同样必须通过本节格式检查，不能因平台已给出建议便接受违规编号。同批新增依次递增，保存前用当前 `cases/list` 复核归属、最大序号及全文件唯一性，再经 `cases/create-preview`、`cases/create` 保存并回读，不盲抄模板或旧建议。
5. **授权非语义整改。** 默认保留既有合规 ID；用户明确授权编号整改时，全面检查当前用例的编号及标题，不仅修正被点名的一条或某种前缀。用 `cases/create-context`、`cases/list` 核对当前摘要、场景、旧编号及目标占用，以 `{experiment_id,expected_sha256,renames:[{from,to}]}` 先调用 `cases/renumber-preview` 核对映射，再调用 `cases/renumber` 保存并回读，不生成或回传整份文件。标题夹带的第二套编号通过 `cases/read`、`cases/update` 只清理名称中的编号，保留业务名称与其他字段。已有部分整改时只处理仍需整改的项；目标被其他用例占用时不覆盖。
6. **区分当前引用与历史。** 改号工具仅替换当前用例标题编号；另行核对并仅同步当前文件内指向这些用例的有效直接引用。不改用户输入、预期业务要求、fast、用例顺序或其他正文。历史 Run、冻结快照及历史出处保持原编号，不追改历史证据，也不把历史出处编号塞回当前标题。
7. **保存前后逐条检查。** 对整份当前用例清单检查编号格式、全文件唯一性、场景缩写一致性、标题仅含一个用例编号，以及当前直接引用是否仍能定位到对应用例；同时核对输入、预期业务要求、fast 和顺序未被非语义整改改变。任一不满足不得宣称规范整改完成；不能只检查 `U-NEW`、只检查主编号而忽略名称中的第二套编号，或以解析通过、保存成功代替本节检查。
8. **修正失败后重试。** 校验失败时按回执修正必要字段，重新预览后再保存；摘要冲突先回读当前状态，保留并行新增与正文修改，再按当前状态处理。不得转用原生文件写入绕过平台校验；结果未知先查询实际状态，不盲目重发。

## 仅调整场景内用例顺序

排序不改变业务语义，直接使用共享用例服务，不生成整份 evaluation.md。先用 `cases/list {experiment_id}` 取得当前 `sha256`、场景及完整 Case ID；只在需要判断分组时读取目标用例。沿用户指定顺序稳定排列各组，组内保留原顺序。例如巡检按“查询巡检项 → 创建周期任务 → 常规巡检 → 深度巡检 → 专项巡检”排列；有不明确归属时先核对目标用例。

用 `{experiment_id,scene,case_ids,expected_sha256}` 调用 `cases/reorder-preview`，核对完整前后 ID 顺序，再将同一参数交给 `cases/reorder`，最后 `cases/list` 回读。`case_ids` 必须是该场景现有用例的完整、无重复排列；不改号、不改标题、输入、预期、fast、注释或其他场景。当前顺序已满足时直接报告，无需写入。摘要冲突先回读并保留并行修改后重新预览；未知回执先查询实际顺序，不盲目重复写入。只改一个用例的文字使用 `cases/read`、`cases/update-preview`、`cases/update`，不重写整份文件。

## 保持兼容

- 用例正文不增加其他独立粗体字段标签。
- 预期内不写一到三级 Markdown 标题，不嵌入另一个 U-* 用例标题。
- 不同用例整组输入去空白后不能完全相同；不要用无意义改写绕过重复检测。
- 同输入不同环境的场景依赖现有执行能力，不臆造平台参数化语法。
- 未显式选择 Case 时，fast 模式取 fast 集合，full 模式取全部用例；显式选择 Case 覆盖默认集合。运行模式的其他默认配置需另外核对。
- 用例在 Agent 的 evaluation.md 维护，历史 Run 的冻结输入和预期不随本次改写变化。

授权保存时沿用现有维护能力，并回读标题、fast 标记、输入和预期；授权运行时沿用现有评测能力。仅改写文本不表示已经执行验收。

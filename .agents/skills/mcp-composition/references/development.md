# 工具组合编排开发方法

供平台管理助手和研发工具开发、优化及验证组合时按需阅读。办理动作使用 [`mcp-composition`](../SKILL.md)；对象归属遵循[数据工作区原则](../../../../AGENTS.md#组合编排资产自包含)。本文维护方法和经验，接口字段、组件实现及运行结果各引用自己的事实源。

## 先判断是否需要组合

以用户任务为单位，先列出原始接口顺序、返回数据的使用方式、允许副作用与结束位置，再与“原始 MCP 工具 + 现有业务 Skill”比较。先核对上游已有的筛选、批量、校验、渲染、冲突分析和状态查询；不重复实现这些能力，不从旧服务、旧包名或已有组合数量倒推拆分。

**固定的多个接口连续调用、返回数据加工、后续调用及异常恢复，尽可能使用工具组合编排。** Skill 负责意图理解、交互、语义判断和选择流程；组合负责确定性的执行与数据衔接。不得因清理过度拆分的旧组合，就把所有固定执行重新交给模型逐步调度。只有单次调用、必须依赖当轮语义判断或真实接口合同尚不明确等情况，才保留相应的原始工具路径并说明理由。

单次查询和依赖用户语义判断的探索使用原始工具与 Skill。连续调用的依赖、字段传递、分支、分页或汇总已经确定时，评估组合能否减少模型往返、数据传输或错误；两次调用也可能需要组合，调用次数不作为准入门槛。现有 Skill 承担发现交互、选择、建议和结果解释，不能据此把固定的数据处理和失败恢复全部交给模型。

只有当前任务确需且有独立价值的确定性执行才建立组合。单接口能力直接复用原始工具；固定调用链按上述原则组合，跨组合复用时使用稳定公开输入输出和固定版本依赖。不为一次调用增加本地业务任务、操作版本、快照摘要、命令槽或审批层；业务状态归上游，平台 Session、Run、回执仅保留追踪。上游要求的 requestId 等幂等字段照实保留，不能因“无状态”删除恢复所需关联。

短接口链应在同次调用返回最终结果、必要明细与失败原因，不能只返回受理后让模型反复猜测查询；长巡检等任务按真实需要异步查询。平台运行 ID 不充当上游业务 ID，具体响应合同引用[平台执行合同](https://github.com/wr5912/harness-engineering-platform/blob/main/docs/platform-design/04_核心业务闭环与服务接口.md)。

固定链统一承担有界重试；返回阻塞终态且没有新事实时，助手不改动无关说明字段后重跑。后续操作以所选动作的真实合同为准，不能从工具的通用停止位置枚举推断每个动作都支持。仅本地生成的输入关联号不能当作已提交的业务回执；失败或本次未执行也不能证明设备当前状态。具体实例与失败证据保存在所属 Run，不在技能复制维护。

审查需给出原始工具基线、上游已承担的工作、组合增加的实际价值和同输入验证证据。例：设备定位→上游预览→保存草稿可以作为原始工具基线；若每次都需确定性校验、传参和原号回读，可比较封装后的效果。否定旧包拆分不等于否定所有组合，也不预设必须创建几个。证据不足时先保留候选与验证问题，不自动发布。

审查同时列出无需组合的用户任务、实际可用的原始工具或公开 Skill 路线及结束位置，并说明每个保留组合增加的价值和不应使用它的条件。业务分类不与组合一一对应；查询目录、读取单项已有事实、查看原运行结果或使用原生周期任务管理，不能仅因属于某类业务就启动对应组合。核对实际执行角色的工具可见性，不能把配置或文档中的原始工具当作已发现能力；同输入对照缺失时，必要性与性能结论保持待验证。

必要性复核必须落实到资产清理：被 Skill 与原始工具完整覆盖、没有独立执行价值的组合，删除其登记、发布包、源码和直接调用入口，不只修改 Skill 路由。仅为父流程转换已有数据的节点并回父包，不另发布子组合。先迁移当前草稿、发布入口及其实际固定依赖；未再被引用的历史版本不作为保留废弃组合的理由，历史 Run 与冻结口径保持原样。

## 从任务到可用组合

1. 明确用户输入、业务结果、允许的副作用和完成条件，先按上节核对原始工具基线、已有 Skill 及真实上游 Schema。已有信息足够就连续执行；只补问影响目标或执行所必需的信息。确需组合时才将固定的数据处理交给组合，语义判断留给助手。
2. 确定复用边界。有公共输入输出的子能力通过已发布组合及固定版本复用；先验证子组合，再组装父组合。自身文件放在 `mcp/compositions/<id>/`，共享模块归 MCP 公共层并显式声明，不读兄弟组合的私有文件。
3. 在本包 `flow.json` 编辑原生 Langflow 节点、端口、连接、组件代码与位置；从真实数据依赖表达分支、批量、并发和汇合。粒度以用户能理解控制流程为准，普通转换函数留在组件内。仅本组合使用的模块放在自身包内，声明与加载格式查看[资产读取实现](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/plugin/src/mcp/lfx-assets.ts)。业务判断使用本包 TypeScript 组件并由原生节点回调；同一业务判断不再另写 Python 实现。发布冻结实际依赖字节。不另写图描述，不从代码提取展示节点。
4. 管理助手通过当前工作区原生文件工具编辑已授权的数据资产，通过平台工具保存草稿、检查、发布、调用和回读；按需 `describe` 查询动作合同。平台源码、依赖安装、构建与装载由研发工具处理。当前原生流程仍需登记对应工作流及输入输出合同；找不到登记或缺少执行能力时明确交回研发补齐，不能编造工作流身份、用脚本调用上游绕过平台或声称已经可运行。
5. 按下面的验证层次取得证据，再在授权内发布。发布顺序从子到父；选择父依赖时读取实际固定版本，并按源码目录及文件摘要核对冻结包。分别判断当前文件、构建时内容与实际装载是否一致；不一致或未核对部分保持未知，不用 Git 提交号或工作树代替装载证据。修改草稿不改变既有发布包，子组合升级后父组合是否升级须明确处理。
6. 实际调用后查原 Run 到终态，按回执读取报告和原始明细；分页读至总数，与汇总逐项核对数量、结论及缺失范围。节点明细为空而报告有事实时，不能按空结果验收；保留原 Run 与不一致证据，交研发修复查询与结果存储的衔接。中断先查原运行，不重复提交。
7. 比较性能前核对计时与计数覆盖的阶段，区分准备、排队和执行开销；报告生成是否计入总耗时、请求数与并发峰值是否覆盖准备阶段，均以运行记录及实现为准。根据同一输入下的结果、上游请求数、并发峰值和耗时判断优化效果；未计量部分保持未知，不将单次成功或局部指标写成端到端收益。执行质量要求见技能，不凭结构声称已经最优。

## 验证层次

| 层次 | 应取得的证据 | 能说明什么 |
| --- | --- | --- |
| 静态检查 | 草稿回读、dry、原生图及端口引用 | 先读取所选组合的实际输入 Schema，按其必填字段和枚举构造 dry 输入；发布复用这份合法输入，不套用其他组合的参数。只验证定义、依赖及输入的静态合同，不构造组件、不访问上游 |
| 官方运行时验证 | 使用锁定的官方 LFX 构造并执行实际流程，隔离真实外部接口边界 | 组件可加载、端口兼容、分支与汇合可执行；不是线上业务通过 |
| 真实业务调用 | 同一固定版本的 Run、原始明细及报告 | 实际上游结果、覆盖范围、错误和未知项；终态完成与业务通过分别判断 |
| 使用方验收 | 管理助手或目标业务智能体的真实任务；Harness 比较保存 Run | 需求理解、工具选择、进度反馈、结果解释和恢复是否完成用户任务 |

验证按实际风险选取有区分力的场景：正常与空输入、分支两侧、独立子项部分失败、超时取消，以及发布后修改草稿不影响固定版本。批量与嵌套场景同时核对结果顺序、并发上限和重复请求复用。dry 失败只修静态问题；只有任务已授权实际验证时才进入执行层，不把执行当作 dry 排障手段。

冻结草稿绑定使用实例的实际来源。Harness 修改后，先完成实例重载、来源绑定更新及业务实例工具发现，再启动验收会话；仅有 `current=loaded` 不能证明草稿绑定仍有效，不在管理准备任务完成前抢跑。

研发复用[官方运行时回归](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/mcp/lfx/test_runtime.py)、[发布资产回归](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/plugin/test/mcp-lfx-assets.test.mjs)和[巡检实际流程回归](../../../../mcp/tests/test.mjs)，不在文档复制测试实现。画布验证在实际页面核对当前选择的草稿或固定版本，以及分支、批量内部流程、子版本和源码来源；截图或页面打开不能代替运行证据。

## 已验证的经验与陷阱

| 问题 | 应采用的方法 | 定位依据 |
| --- | --- | --- |
| 分别维护执行代码和画布节点，无法保证控制流程一致 | 同一原生 flow 供官方执行器和画布读取，发布冻结流程、模块和子版本 | [资产与画布实现](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/plugin/src/mcp/lfx-assets.ts) |
| 互斥出口直接共享消费者，或浅/深终止路径汇入同一总出口，导致混入未选值或被跳过的深分支依赖挂住 | 浅/深终止路径使用各自独立的原生 terminal output，可复用同一 TS 结果函数；只有实际存在共同后续步骤时才经独占分支顶点作局部原生列表汇合，严格核对输入数量。真实图覆盖早退、错误、深层及跨 Run 查询，断言每次仅一个有效终态；不去重掩盖、不删断言、不补丁官方 scheduler | [官方分支回归](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/mcp/lfx/test_runtime.py) |
| 父流程汇总输入名 `status` 与 LFX 保留字段冲突，dry 通过仍执行失败 | 修正原生组件输入、模板和边的目标端口，并用官方运行时执行父流程；不手工维护另一套保留字表 | [巡检流程回归](../../../../mcp/tests/test.mjs) |
| localhost 回调受机器代理环境影响，流程服务可启动但流式调用失败 | 平台内部回调的网络策略与外部连接分开处理，验证官方 HTTP/流式入口 | [运行时回归](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/mcp/lfx/test_runtime.py) |
| 资产或规则缺失、上游响应异常被当作正常或空结果 | 校验真实响应结构，保留 failed、unknown 和未覆盖范围，汇总不能抹去子项失败 | [巡检结果合同](../../../../mcp/src/inspection/index.ts) |
| 原生运行报告有事实，节点明细却为空 | 区分节点进度与业务结果，从已保存结果解析父子明细并核对分页，不为查询重复执行或复制全量结果到各节点 | [嵌套明细回归](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/plugin/test/mcp-workflow-runs.test.mjs) |
| 助手猜测图或源码查询版本字段，错误后反复尝试 | 查询当前动作合同，分别使用当前选择和固定版本身份，不混用不同动作的选择方式；合同与实现冲突时保留回执交研发修正 | `platform_mcp describe` 的当前合同 |
| 发布成功、进程启动或文件更新被写成完整验收 | 分别核对固定发布包、实际加载、真实调用和使用方任务；未知结果先回读 | 上表各层证据 |
| 实例资产已更新、草稿已绑定，但业务会话仍看不到工具 | 核对实例原生连接及真实工具发现；分组快照和调用必须使用同一实例草稿上下文。不同实例并发访问时验证目录隔离，不以平台侧发现代替业务实例调用 | [分组路由回归](https://github.com/wr5912/harness-engineering-platform/blob/main/platform/plugin/test/mcp-group-v2.test.mjs) |

实现缺陷先修共同根因，复用或补充必要回归，再将有复用价值的方法合并到本文；单次运行详情保存在对应 Run 或平台验收证据中。组合 README 只导航自身内容，不放开发日志、参数副本或其他组合的说明。

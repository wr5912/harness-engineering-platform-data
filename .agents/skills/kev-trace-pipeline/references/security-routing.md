# 网络安全八类业务意图路由：有界参考合同

`cybersecurity-routing-v1` 将已满足边界条件的 DSH 决策前缀投影为一题 `agent_route`。静态定义位于 [`assets/security-routing-contract.json`](../assets/security-routing-contract.json)，合同版本为 `cybersecurity-routing-contract/v1`；输入构造器版本为 `security-routing-input/v1`。原始数据题型中的八个中文候选键和通用职责得以保留，未复制真实输入、原始记录或标签。

这是离线业务意图分类任务的参考投影。八个名称表示候选职责，不证明平台上存在八个对应 Agent。抽取结果的 `candidate_bindings` 始终为 `{}`；`deployment_ready=false`。本合同没有覆盖全部安全业务，也没有完成在线执行接管。

## 1. 一题究竟判断什么

目标是判断当前尚未作出路由决定的**主要业务意图**。它不输出工具名、执行参数、报告内容或后续整个工作流。请求的回复格式（例如“用表格回答”）不改变业务类别；实际动作是否可执行另行核对权限、参数及实例状态。

| 候选键 | 职责边界 |
| --- | --- |
| 威胁研判 | 判断具体告警、事件或可疑行为的威胁性质、置信度及处置必要性。 |
| 响应处置 | 执行具体事件的应急止损动作，或形成具体处置剧本。 |
| 策略生成 | 创建、维护、下线或检查安全设备的访问控制及协议检查规则。 |
| 安全巡检 | 主动盘点、扫描、检查运行状态、配置基线和业务连通性。 |
| 故障排查 | 输入有依据地指向安全产品、平台或设备的已发生异常，并定位原因和修复方向。 |
| 知识问答 | 询问概念、产品功能、一般运维或配置方法及操作流程。 |
| 报告生成 | 整理已有安全业务结果形成报告或总结。 |
| 其他（兜底） | 有充分可见依据确定请求处于前七类职责之外。 |

精确职责以静态合同的 `question.criteria` 为准。候选排列次序没有业务优先级含义。

### 首要动作和多任务

用户明确“先做甲，再做乙”时，以当前待做的首项业务为目标；必须能从当时可见用户请求确定这个顺序。若用户明确主要目标，同时提出格式要求或依附该目标的交付要求，依据主要目标判断。以下仅是合同解释的人工示例，不是从真实轨迹抽取的标签：

- “先判断这个告警是否真实，再决定是否封禁”：当前首项是威胁研判。
- “对已确认的事件执行封禁，并附上执行摘要”：当前首项是响应处置。
- “根据已有巡检结果写周报”：当前任务是报告生成。

没有已授权的跨类别默认优先级。对于“同时研判告警、生成长期规则并写周报”等并列独立任务，如果用户没有给出首要目标或顺序，复核者应标记 `ambiguous`、记录缺少的优先级依据，并澄清或另行审定业务合同。不得以候选顺序、历史实际动作、将来结果、风险想象或通用领域偏好发明金标。构造器不进行这类语义判断，也不生成规则标签。

### 兜底和信息不足

“其他（兜底）”只表示职责范围之外。它不表示工具不可用、执行参数缺失、任务优先级不明或背景证据不足。例如，明确要求“执行事件应急封禁”但缺少目标地址，可能已能确定业务类别，执行仍需补参；“继续刚才那个”却没有可见背景，连路由类别也不能确定，应留待复核或澄清。

八类题没有新增 `clarify` 选项。不能唯一归类的样本不应被强制变成八选一金标；复核为 `ambiguous` 的记录不进入常规金标评估。在线系统必须在调用分类器或采用结果的外围单独配置澄清与回退流程；本投影没有实现自动歧义识别或可信度门禁。

## 2. 只接受真正尚未作出的初始路由边界

本版本自动支持的范围同时满足：

1. 日志从 DSH v4 会话头及连续前缀开始，受影响的快照没有阻断审计问题。
2. 会话没有 `isSeeded=true` 或 `parentSession`，不存在需要核对的继承上下文。
3. 当前是会话内第一次模型响应，此前没有任何 assistant 消息、`tool/call` 或 `tool/result`。
4. 当前 surface 中存在 `source.kind=user` 的实际用户消息，且最新实际用户消息仍可见。
5. 当前请求头和输入内容处于下述支持范围。

审计器在应用当前响应前保存 `prefix_context` 中的前缀计数及 `latest_actual_user_seq`。这些计数来自完整日志，不通过当前 surface 是否存在旧消息来猜测，因此替换或压缩 surface 不能把已经执行的步骤重新包装成初始路由。

轮询、执行后总结、报告生成步骤、工具重试及后续模型响应返回 `not_initial_routing_boundary`，`disposition=skip`。后续新增一条用户消息，也不能凭这一点证明发生了新的业务路由边界；本版本仍跳过。

真实后续路由点可能存在，但目前没有已核对的 Harness 触发协议。要支持它，需先提供能够证明“本次确实启动新的业务路由、路由决定尚未发生、关联请求及所需背景完整”的真实事件定义，再实现并测试新的前缀边界判定。不能给每个 LLM 响应添加一题 `agent_route`，也不能事后插入标志冒充线上证据。

## 3. 前缀状态、证据和范围限制

模型输入由两个固定字段组成：

- `state.用户输入指令`：当前可见的最新实际用户消息的原文。
- `state.背景信息`：其他当前可见的 `user/message` 且 `source.kind=user` 消息，按 surface 次序以文本数组逐条保留原文。多文本块仅以换行连接，不生成摘要。缺少真实用户背景时保留空数组。

每条被投影消息都有 `provenance.state_evidence_refs` 中的真实行号、事件序号和内容路径。引用必须小于当前 `decision_seq`。系统、开发者、工具及框架注入仅用于完整前缀审计，不进入业务 state；即使事件名是 `user/message`，只要 `source.kind` 不是 `user`，例如 `runtime-context`、`skill-catalog` 或 `agent-instructions`，也不冒充真实用户业务背景。被排除消息的引用保存在 `provenance.excluded_context_evidence_refs`，数量保存在 review；原始 `snap.surface`、完整可见事件序号、prefix digest 和源轨迹保持不变，可据此回查。

这个来源白名单对应“用户表达的业务意图分类”任务，不承担框架指令遵循、权限判断或工具选择。监督标签必须由**投影后的业务输入**支持。若用户指代只有在被排除的框架注入或系统背景中才可解析，应认定当前投影上下文不足，留待复核或澄清；不能借完整前缀的隐藏事实沿用历史标签。如果业务确实需要接收这类背景，应另行核对最小来源和字段白名单、版本化输入合同与证据路径后重新抽取，不能自由补写摘要。用户自己提供的历史描述只能按可见原文保留，不宣称还原了未提供的历史。

`request_header` 是当前边界的已记录环境，必须存在有效 tools 列表；其中工具名不会改写八类候选，不会产生 Agent 映射。此离线任务不将模型名、工具目录及执行参数放进业务状态。若真实部署需要依赖能力可用性决定可路由对象，应设计另外的版本化输入与运行时绑定合同。

固定投影范围为最多 **16 条真实用户业务消息**、这些原文合计最多 **16,000 个 Unicode 字符**；被排除的框架说明不占用业务投影消息数或字符限额。被选中的用户消息只支持纯文本；其中出现未建模的非文本内容、缺少请求、缺失边界证据或超范围输入均保留复核原因并拒收，不静默丢弃业务内容。字符限制用于明确此参考投影的覆盖范围，**不等于 token 数，也不证明符合 KEV 或任何模型的上下文窗口**。

当前响应的 `observed_action`、用量和未来终态不会进入 `state` 或 `question`。历史动作仅在监督侧原样保留，`observed_candidate` 不自动映射；抽取标签始终 `unlabeled`、值为 `null`。真实用户背景改变应改变 state；框架说明、当前动作或未来结果改变，不应改变当前业务模型输入。

候选证据只引用真实静态合同：`kind=contract`、`contract_version`、资产相对路径和资产文件字节的 SHA-256。不能拿当前工具目录或未来 Agent 名称假装这些八类候选已具备执行能力。

## 4. 构造器与逐步交接

`scripts/trace_adapter.py:build_sample(snap, profile="cybersecurity-routing-v1")` 进入本投影，`extract(audit, profile)` 沿用原有抽取流程。业务实现位于 `scripts/security_routing.py`。

纯函数入口：

```python
from security_routing import build_routing_input

projection, reason = build_routing_input(
    snap["surface"],
    snap["request_header"],
    decision_seq=snap["decision_seq"],
    prefix_context=snap["prefix_context"],
)
```

成功时 `projection.state` 与 `projection.question` 就是离线与线上应共用的输入；`state_evidence_refs`、`candidate_evidence_refs` 及 `review` 属于旁路元数据。失败时返回 `(None, reason)`。该函数不接受当前输出、后续结果或人工标签，不修改入参，不执行日志中的任何动作。

低能力管理模型应按回执逐步推进：

1. 审计真实输入，确认前缀没有阻断问题。
2. 用本 profile 抽取；检查接收数与每条跳过/拒收原因。零条样本可以是正确结果。
3. 逐条复核当前主要任务、背景是否足够、八类职责及多任务优先级。补证必须可追查；未知背景不能自由补写到原 state。
4. 保存人工标签及依据后，才进入编译、来源家族分组和独立切分。抽取器不自动生成 `verified`。
5. 用真实训练编码器检查完整 state、固定 question、特殊 token 和模型实际预算；超预算记录不允许盲截断后继续。

在真实在线接入前，还需要单独核对目录和部署合同：每个业务类能否映射到实际存在的 Agent、稳定标识与版本、当前可用性和权限；未知映射继续留空。运行时应复用同一构造器及静态合同，使用真实完整前缀维护 `prefix_context`，不能将短 surface 的计数直接填零。

还需配置缺信息、歧义、低置信度、缺映射和输入超范围时的业务回退；核对执行参数、权限、执行回执和后续路由点。完成这些事项并取得实际等效验收证据前，本 profile 只交付可审计的离线意图样本，不表示部署接管就绪。

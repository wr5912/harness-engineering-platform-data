# 对抗式 Skill 审查准则

本准则用于人工/Agent 审查。先完成 [规范、内容与工整性检查表](format-and-structure.md) 的逐项覆盖，再判断实际收益。每项以证据填写通过、不符合、不适用或未验证；不以自动脚本零命中代替语义审查，也不为统一版式扩张 Skill。

## 1. 十二个维度

| 维度 | 对抗式问题 | 有价值的证据 | 常见整改方向 |
|---|---|---|---|
| 必要性与边界 | 不用 Skill 是否已足够？是否把工具/工作流逻辑混进 Skill？ | 无 Skill 基线、任务实例、现有能力清单 | 删除、拆分、合并或缩小职责 |
| 执行主体与 Skill 配置 | 哪些任务留在主智能体，哪些值得委派？执行者是否实际获得所需 Skill、工具和上下文？ | 独立输入/产出、目标运行时配置、委派/汇总记录 | 保留主流程，或给必要的子智能体按需配置既有 Skill |
| 集合规模与任务覆盖 | 实际可见入口是否覆盖所需任务？是否竞争、碎片化、遗漏或隐藏关键能力？ | 分作用域清单、任务—入口映射、描述/加载成本、集合路由用例 | 精炼描述、调整可见范围、合并冗余；数量由效果决定 |
| 跨 Skill / Agent 控制流 | 是资料引用、加载指令，还是实际委派？交接、分支、循环、共享状态和失败恢复是否清楚？ | 带类型的依赖/流程表、条件与退出、父子 Trace、状态所有者 | 拆参考、拆 Skill、合并执行边界或下沉确定性步骤 |
| 发现与触发 | 正例能触发，邻近请求不会误触发吗？ | 真实/合成的正负样例、触发日志 | 精炼 description，说明适用/不适用边界 |
| 格式与兼容性 | 入口、YAML、必需/可选字段符合哪一版规范？目标扩展是否受支持？ | 官方条款、解析结果、参考工具与原生回执分别记录 | 修正真正不符合项；扩展与可移植性分开判断 |
| 内容与指令工程 | 必要输入、方法、分支、产出和异常边界是否充分？是否空洞/冲突/强制过度？ | 内容逐项定位、失败轨迹、任务类型 | 补真实缺项、删除冗余；不以有标题代替有方法 |
| 文档工整性 | 标题、段落、编号、术语、表格、代码和链接是否清楚一致？ | 正文/参考定位及实际歧义 | 修排版与表达问题，不发明官方固定章节要求 |
| MCP / Tool 耦合 | 具体名称、参数是否当成永恒接口？ | 引用位置、MCP 工具清单及版本变化、运行错误 | 能力契约、稳定别名、兼容映射、契约测试 |
| 编排边界与成本 | 哪些工具序列无须模型逐步判断？ | Trace、调用次数、固定依赖链、中间结果大小 | 下沉同域复合工具/跨服务组合 MCP/局部脚本 |
| 产物与评估 | 是否有可观察完成条件？是否与无 Skill 对照？ | 产物、grader、回归测试、重复运行数据 | 明确定义验收和代表性测试集 |
| 风险与演进 | 脚本、副作用、外部依赖、状态存放是否合理？ | 实际权限、脚本代码、离线部署条件 | 只修实质风险，隔离可变数据并最小化依赖 |

三项架构问题的输入、判据与交付按 [架构专项](architecture-review.md) 执行。每次判断适用性；单文件审查缺少集合、配置或运行记录时只作有依据的局部判断。三项是本地质量要求，参考官方设计建议，不新增官方格式义务。

## 2. “先 Steelman 再 Attack”

**Steelman（先为作者辩护）**：这份 Skill 为哪种不可替代的任务提供知识？避免重复模型已有能力的理由是什么？为何当前自由度合理？

**Attack（再攻击设计）**：删掉它会损失什么？是否可以用 1 个确定性脚本代替？是否有可复现的负样例证明 description 太宽？工具名变动后哪些步骤失效？某些指令是否要求 Agent 过度规划？

不要为了产生问题而捏造问题。可以给出“没有发现 P0/P1 的证据”的结论。

## 3. 严重度（影响优先，不以语气升级）

| 等级 | 判定依据 | 例子 |
|---|---|---|
| P0 / 阻断 | 已有证据证明 Skill 无法加载/必然失败，或含确证的重大危险行为 | name 不合法导致加载失败；运行中确证越权不可逆修改 |
| P1 / 高 | 高频路径显著受损或明确架构耦合导致重复故障 | 实测 MCP 重命名后核心功能失败；多数正向请求误触发 |
| P2 / 中 | 有明显可维护性或效率改善空间，但后果尚有限 | 可以缩小的指令冗余；过细编排存在合理改进方向 |
| P3 / 低 | 可选风格/文档便利改进 | 示例排序、细微措辞 |

P0/P1 应尽量附复现步骤或可核查事实；仅有静态线索应标注“潜在问题/待验证”，避免冒然严重定级。

## 4. 每项发现最小证据结构

- `ID`、级别、类型：**确证 / 静态线索 / 待实验假设**。
- `适用规则`：官方规范/参考实现策略/目标运行时/本地质量，附来源与版本；官方建议注明性质。
- `定位`：`SKILL.md:42-49`、脚本文件行号或运行 Trace ID。
- `证据`：最少量必要原文或轨迹，不复述整份 Skill。
- `机制`：为什么会伤害触发/执行/可靠性/维护。
- `改变建议`：删除、精简、替换、拆分、下沉（精确到文件或片段）。
- `取舍`：改变可能造成什么损失；为何选这个而不是复杂方案。
- `验收`：用什么正负测试或对照能够证实变化。

## 5. 反过度工程守则

- “增加严格审批”“增加治理层”“新增专门数据库”“为所有步骤添加强制检查”不得当作默认正确答案。
- 缺少证据时，不要求重构运行时或创建平台服务。
- 某个工具名被引用，不等于存在硬耦合缺陷；稳定公开 API 完全可以直接调用。
- 三个工具调用不一定比一个工具调用差；效率结论应在相同任务与模型配置下实测。
- 固定流程不应把需要上下文判断的决策节点完全硬编码。
- 给出裁决：**保留 / 简化 / 合并 / 拆参考 / 拆 Skill / 委派子智能体 / 下沉脚本、工具或确定性编排 / 废弃 / 证据不足**。具体到受影响任务或子流程，允许“不整改”。
- 不规定通用最佳 Skill 数量或委派深度；数量少、正文短、调用少都不能独立证明设计更好。低频能力先看是否仍承担必要任务。
- 拆分要说明新增的独立任务边界及交接成本；合并要保留真实不同的作用域、生命周期和验收。新增子智能体不必新增或复制一套 Skill。

## 6. 严格合规的结论边界

- 所有已发现的官方硬要求不符合项都要报告；摘要可分优先级，完整记录不得只留 3–5 项。
- 格式、参考工具、目标运行时、内容、工整性和行为验证分别给状态；未运行或未读取不记为通过。
- 官方规范没有统一正文章节模板。内容缺失可判为本地质量问题，但不得把缺少同名标题伪称官方违规。
- 参考工具成功、检查器单测成功、原生加载成功都不能单独证明完整合规或任务有效。

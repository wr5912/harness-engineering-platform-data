# MCP 耦合与编排专项审查

目标是识别两个在真实开发中易发生的故障：**易变接口名称硬编码**、**细粒度工具过度交由 Agent 编排**。同时防止把任何明确接口调用都误报为问题。

## A. 工具名称与能力契约

1. 提取 `SKILL.md`/引用文件中的连接或分组身份、公开工具名称、资源地址、参数名、调用顺序；定位文件行号。
2. 检查这些名字是否为受管理、稳定、版本化的契约，还是迭代中经常重命名的实现名。
3. 若有实际工具定义，核对输入 schema、输出字段、副作用及权限；只读资料不足时标注为待核查。
4. 判断是否存在工具发现（如 MCP `tools/list`）、稳定别名、适配器、兼容性测试等机制；**MCP 工具发现不自动承诺重命名语义兼容**。
5. 建议最小修复：先保证兼容别名或契约映射，其次在 Skill 中保留任务能力语义。不要为一个稳定接口建立大型语义路由平台。

### 本平台的公开命名边界

本平台 MCP Manager 的 v2 分组对下游公开 `mcp__<group.id>__<tool>`：中间段来自稳定分组 ID，不是组内服务的显示名。先读取实际分组与工具发现结果，核对分组 ID、工具名及 schema；只改变服务显示名不能证明下游工具改名，也不能用显示名拼接调用名称。

直连 MCP 或 v1 连接可能仍使用 `mcp__<server>__<tool>`；按该连接实际合同判断，不将 v2 分组规则套到所有环境。名称变化的影响须以实际公开名、映射或失败回执为据，不能从命名外形推断。

### 可接受的直接命名

- MCP 工具本身是稳定且被明确维护的内部 API；版本兼容可测试。
- 作为**示例**出现且注明以运行环境可用工具为准。
- 特定运行环境的 Skill 对该工具具有明确依赖，缺失时能报告而非猜造。

### 应重点质疑的写法

```markdown
1. 调用 mcp__old_group_id__get_agent
2. 调用 mcp__old_group_id__get_config
3. 调用 mcp__old_group_id__do_test
```

以上是待审查写法示例，不证明这些工具存在。只有分组 ID、公开工具名或对应接口确实变化，且缺少发现/映射/兼容策略时，才形成相应耦合风险；服务显示名变化本身不够。

### 推荐表述

```markdown
获取目标 Agent 的版本化配置并进行回归验证。
调用前依据当前已发现且符合能力契约的工具确认输入/输出。
如没有兼容工具，说明缺失能力；不要猜测工具名称。
```

如果只需要一个固定工具，保留确切稳定名称并进行契约测试往往更简单。

## B. Agent 编排链是否过长

**静态审查可提出假设，实际优化要看执行轨迹。** 记录：模型参与轮次、工具总调用数、固定操作序列、中间结果输入模型的 Token、失败/重试、成功任务成本。

检查能否抽取**无需新业务判断、顺序相对稳定、输入输出清晰**的子流程，例如：

- 列出版本 → 获取文件 → 校验 schema → 计算 diff → 聚合报告。
- 多个服务依次读取数据 → 关联 → 规范化 → 返回简洁统计。

判断下沉位置：

| 特征 | 首选位置 | 边界 |
|---|---|---|
| 本地、单次、仅某 Skill 使用的确定性操作 | `scripts/` | 运行环境有依赖和权限；脚本不应该是不可见的全局服务 |
| 同一领域 MCP 内部反复调用的小工具 | 原 MCP Server 复合接口 | 原服务维护者掌握事务/错误语义 |
| 跨多个 MCP Server 的固定流程，多个 Agent 复用 | 组合 MCP 或工作流服务 | 公开稳定的任务级接口；处理失败和版本映射 |
| 非确定分支、策略权衡、复杂用户意图 | Agent | 不应强压为固定流程 |
| 长期运行、审批、回滚及副作用管理 | 应用工作流/状态机 | 不能只靠 Skill 文本保证事务性 |

**反面模式**：`manage_everything(action, options)` 之类万能 MCP 工具往往隐藏复杂参数和故障；只为减少工具个数不等于更可靠。

## C. 适度具体的整改格式

```text
问题：xx 工具硬编码已失效的分组 ID 或公开工具名，接口变化后调用失败。
证据：SKILL.md:41-46 + 实际失败日志（若有）。
建议：在适配层保留旧别名，或把名称依赖替换为稳定能力接口。
验收：服务显示名变化但公开名不变时仍可调用；实际公开名或 schema 变化时，经兼容映射找到正确工具，或明确报告缺口。
```

```text
问题：6 个固定且确定性的操作每次都经 Agent 重新规划。
证据：重复运行的工具 Trace 与固定参数流（无则仅标待验证）。
建议：优先同域复合 MCP；跨域采用轻量组合 MCP。Skill 保留策略与验收。
验收：对照成功率、模型轮次、总 Token、Token/成功任务和延迟。
```

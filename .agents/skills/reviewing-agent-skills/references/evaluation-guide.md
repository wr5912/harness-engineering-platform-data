# 轻量评估与回归指南

此文档提供**建议方法**，不宣称本技能已自动完成模型评估。从有区分度的真实或可复现实验任务开始，覆盖相关正向、负向、异常与边界；测试数量依任务风险及失败分布调整。

## 0. 先分清验证对象

- 检查器单测：只验证检查工具的行为；不等于任何目标 Skill 完成规范验收。
- 目标静态检查：官方条款、参考工具与本地检查结果分别记录；有命令回执才写实际执行。
- 内容与工整性：按 [检查表](format-and-structure.md) 逐项定位，由人工/Agent 审查；标题或关键词命中不替代内容判断。
- 原生与任务验证：分别记录发现、加载、调用面及产物结果；未运行不写通过。
- 集合与架构：按 [架构审查](architecture-review.md) 区分静态依赖、声明控制流与实际 trace；Skill 引用、正文加载和独立子 Agent 执行分别取证，不替代单项规范检查。

修订检查器时至少覆盖：坏 YAML/重复字段、字段形状、合法 Unicode 与 DSH 差异、合法无固定标题、空洞正文仍需审查、缺依赖受阻、真实缺文件、工具动作不是路径、目标脚本不被执行。官方参考不支持的表示不能包装为目标原生已失败。

## 1. 两类不同的评估

**发现/触发测试**：是否应当调用该 Skill？记录 `expected_activation`、`actual_activation`。计算：

- Precision = TP/(TP+FP)，避免误触发。
- Recall = TP/(TP+FN)，避免漏触发。

**执行/结果测试**：对正确触发的任务，检查真实产物、必需步骤、外部工具效果和任务成功率。与无 Skill 基线比较，不要用主观语言质量分数代替。

### 集合路由与执行主体

- 集合测试记录该场景的必选、可选、禁止 Skill，以及允许的组合 `allowed_activation_sets`；多标签协作和可替代组合可以合法，不强制互斥或唯一入口。
- 将实际选择与允许组合对照，分别报告错选、漏选、无必要的重复加载及受影响任务；不要把所有允许组合的并集当作单一必选答案。Precision/Recall 按已声明的必选与可选口径计算，分母为零记不适用，未观测不计成功或失败。
- 记录预期与实际执行主体 `expected_owner` / `actual_owner`，核对主 Agent、子 Agent 各自可见目录、实际加载正文、可用工具及产物责任。父级能看到或加载 Skill，不证明子级可见或已使用；同一主体加载多个 Skill 不等于委派。
- 对合并或拆分建议，验证输入、关键约束和输出能否跨边界完整传递，谁汇总、谁验收、谁恢复失败；以实际装配和版本为证，不套用其他运行时的字段语义。

## 2. 真实世界对照

- 围绕待验证假设选择相关方案：原方案、仅整理引用且保留职责和执行主体的最小方案、按任务拆分或合并 Skill 的方案、确需独立执行的子 Agent 方案；可另选无 Skill 基线。不要求所有组都运行，也不预设拆分更好。
- 对齐模型、温度/推理参数、输入任务、工具权限、资源版本、预算和初始状态；对子 Agent 同样记录这些条件。结构差异及无法对齐的条件单列。
- 各组多次重复，记录波动；环境异构时明确不可直接横比。
- 对比任务成功率优先，之后看模型参与轮次、工具调用数、Token/成功任务、延迟及重试率。
- MCP 工具改名/Schema 变化使用兼容性案例；不只验证“命名在文档中替换了”。

### 控制流与恢复

选择能检验假设的正常路径、相关分支和失败路径，将声明步骤与实际 trace 对照：前置条件、分支选择、交接、汇合、退出及验收是否一致。合法有界修复要验证终止和失败出口；资料互相引用只构成静态环，不能直接判为执行死循环。

涉及重试或并发写入时，在已有授权和可控测试条件下检查写入结果未知、取消、子任务失败后的恢复、重复写和共享产物冲突；观察交接是否丢失输入、关键约束或证据。没有执行条件就保留设计与 `NOT_RUN`，不自行执行目标代码或新增外部动作。

## 3. 证据与成本

- 没有运行轨迹时，只能**提出可检验的优化假设**，不能断言“Token 已减少 80%”。
- 工具调用数 ≠ 模型推理轮次；区分模型驱动的调用与组合工具内部的确定性调用。
- 分别记录常用路径的正文/引用加载量、上下文峰值和全部父子执行的输入/输出 Token；总量包含重试与失败尝试，不能只看父级上下文缩短。采集范围不完整时标未知，不补零。
- 延迟报告用户等待的端到端时间；并行子任务时长之和不等于端到端延迟。记录失败恢复、重复写与交接损失，避免用更低成本掩盖结果退化。
- Skill 数量、行数、分支数及依赖深度仅作解释线索，不设官方最佳数量或复杂度阈值；低频但关键的能力单列覆盖，不因平均使用率低就判无价值。
- 如果任务成本极高，可先运行最有区分度的少量测试，再扩展失败附近案例。
- 测试报告应保留未执行/环境不兼容/无法判定的分类，而非计入失败或成功；未执行填 `NOT_RUN`，静态可读与配置存在不代表路由、原生执行或业务通过。

## 4. 改动与回归

1. 为每个 P0/P1 问题写一个稳定复现用例。
2. **最小修改**（优先删去冗余，只有必要时才加新指令/工具）。
3. 原始案例与新增案例都重新运行。
4. 检查是否发生新错选/漏选、合法组合被排除、关键低频任务退化、执行主体不可见、交接损失、重复写或总成本增加。
5. 不通过时明确结论“修复未验证/未达预期”，不要无限自动改写。

样例触发请求见 [trigger-cases.json](../tests/trigger-cases.json)，架构任务的合成输入与检查点见 [architecture-cases.json](../tests/architecture-cases.json)。行为评估只向干净执行上下文提供目标 Skill、请求和原始输入；检查点留给独立判定，不传入预期结论。这些是人工/Agent 可读的测试输入，不是会自动启动 DSH/Claude Code 的执行套件。

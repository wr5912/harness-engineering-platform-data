# 威胁事件通知、图标与首页布局整改记录

本记录保存 2026-11-14 UTC 的实现与验证事实。当前 Harness 以 business-agents 中 `agents/security-operations-expert/dsh` 为准；实例 assets 已软连接该来源。目标实例为 `security-operations-expert-12017d4587d1`，入口 `http://172.16.138.228:18506/assistant/`。

## 真实链路与根因

仅发送一次用户指定消息 `请研判以下威胁事件：INC-20261114-000029`。主会话为 `81158257-f7b0-4695-9a1b-e846eada58b5`，子会话为 `9b25ca01-dc0a-48f1-9668-20fb2e7c2ee1`，业务 run 为 `27e517f0-cba2-4265-8f5d-b31eef2e2b10`，研判记录为 `JDG-2121432378677989377`。状态实测经过 IN_PROGRESS、DONE，证据增加后变为 STALE；保存结论为 SUSPICIOUS、置信度 0.55。没有重复提交研判或执行处置。

旧页面把生命周期 NEW 当成“待研判”，没有查询权威 judgeStatus；同一事件旧 investigationStatus 又是 FAILED，因此旧通知不能代表本轮结果。通知轮询重复读取存储快照，活动刷新标记没有触发详情查询；相同负载哈希去重还会吞掉后续刷新信号。真实监听期间未收到本次认领/结果对应的状态通知，随后核对更新后的后端主线，确认相应写入链路缺少统一发布钩子。现场另有 8 次详情读取超时。匿名 guard 提前退出使重复委派未被阻断，出现过深度限制错误后恢复；这不是侧边栏不同步的直接原因。

原始抓取保留在实例 `state/incident-000029-trace/`，历史诊断不覆盖。本目录仅保存目标事件和验证结论，不复制凭据、原始全部通知或其他事件详情。

## 已实现

- 删除独立研判按钮；点击通知行展开/收起详情。每次展开先核对权威状态，仅从未研判事件追加可读草稿，实际存在名称/描述才填写；保留已有文字，不自动发送。
- 同一事件成功填写后三秒内不重复填写，输入已有同一 ID 时不重复；清空并超过冷却时间后再次展开可填写。收起后返回的异步查询不填写。正在研判、已完成、失败、待复核和未知状态只展示详情。
- 新增只读状态接口：核对可信用户可见事件，经既有 MCP 资源读取；按用户、实例、分组及 URL 隔离缓存，合并并发、限制超时，失败保留上次状态。可见页面每五秒对账；重复 NATS 信号仍失效缓存，旧版本不覆盖新结果。
- 修复匿名独立实例的 guard 装载；存在业务 Runtime 时要求可信身份，不降级到 owner。
- 首页标题、主智能体、每个子智能体和每张数字员工卡片均支持独立图标。卡片编辑支持当前浏览器覆盖；无配置或加载失败回退原 GIF。配置合同见业务资产 `security-operations-ui/README.md`。
- 隐藏 workspace/preset 选择行；标题不收缩，首页从可见顶部布局；长文本在最高 `min(32dvh, 260px)` 的输入区域内滚动。CSS 使用语义类名后缀，不依赖现场哈希。
- 后端增加同事务状态版本与发件箱，覆盖认领、完成、失败、证据变化和租约到期；稳定事件 ID、权限收件人查询、发布确认及退避重试。后端代码位于独立工作树 `/home/luopeng/work/ai-soc-judgement-sync`，尚未部署。

## 后续：点击未研判卡片未填入草稿

真实页面复现了 INC-20261114-000032 展开后草稿为空，状态查询返回 query_unavailable。直接读取 SOC 事件详情的一次耗时为 9741ms，超过原来的 5000ms 限制；原读取器还把发现与所有资源读取共用同一个超时信号，排队后的事件可能在开始读取前就已超时。另有独立的前端竞态：后台轮询启动后覆盖点击查询的序号，使有效的点击结果被当成旧响应丢弃。这两个代码问题均先通过新增回归测试复现，再验证修复。

资源发现与每次读取分别计时，状态读取等待上限调整为 15 秒；点击查询期间跳过同一事件的轮询。卡片展开显示查询进度，临时读取失败自动重试一次；重试后仍不可用时提示重新展开。仅新鲜且从未研判的状态允许填写，收起、切换或卸载后不填写。上游详情接口为何间歇变慢尚未定位到其内部实现，本次修复不声称已消除上游延迟。

## 后续：同一事件合并卡片与更新前移

现场原有 200 条通知涉及 37 个事件，32 个事件出现多张卡片，最多的同一事件出现 11 次。根因为展示层把每条活动、状态、完成通知直接当成独立卡片；批量通知还会与单事件通知重复。此次以事件 ID 投影为稳定卡片，批量消息拆分到各事件；通知原始记录及既有保留策略不变。

收到后续通知或对账发现状态、结论、证据版本变化时，更新原卡片并按更新时间前移，保持展开状态。首次查询仅建立基线，轮询时刻、重复读取及暂时失败不影响排序。原生独立存储域保存每个用户/事件的状态指纹、版本和更新时间，不复制事件业务详情。每个事件独立已读；新更新恢复未读，旧版本的延迟已读请求既不会清除新版本的未读，也不会撤销已确认的已读。

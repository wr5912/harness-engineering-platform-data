# f237 → f610 合并清单

## 1. 结论

f237 是新架构，f610 是旧架构。合并方向是**用 f237 覆盖 f610**，把 Workbench 中间服务、受信确认器、部门策略任务这一整套旧件下线。

| 维度 | f610（旧） | f237（新） |
| --- | --- | --- |
| AISOC 固定链 | Workbench 中间服务 + 高层原语（`policy.prepare` / `emergency.prepare` …） | DSH + 内部 LFX 编排（`policy_change` / `emergency_action` 组合）+ AISOC 直连 |
| 确认机制 | 受信确认运行时插件 + 签名提交 | DSH 原生 `ask_user_question` 两阶段确认 |
| 部门策略 | 独立分支 + 本地持久化任务 | 无，统一为批量 `changes` |
| 业务状态 | 本地 Platform 控制器 + 业务台账 | 仅上游，`business_state: upstream-only` |
| 处置运行时 | `disposition-runtime` + 研判后处置 | 无 |
| 工具边界 | 精确 MCP 工具白名单 + role-tool-matrix | 原生绑定目录 + 原生权限 |
| 两层路由 `routeKey` | 无 | 有 |
| XX 设备 | 无 | 有（2 Skill + 2 组合） |

关键证据：

- f237 的 `security-operations-guard.mjs` 只依赖 `mcp-tool-identity.mjs`；f610 的 guard 还依赖 `policy-configuration-guard`、`emergency-action-guard`、`policy-resource-identity` 三个旧件。
- f237 的 `control-boundary.yaml` 已写入 `local_platform_controller: absent`、`enforcement: skill-intent-and-stop-plus-native-composition-fixed-chain`，并删除了 `trusted-confirmation-isolation`。
- f237 的 `harness.yaml` 已删除 9 个 Workbench 相关环境变量（`POLICY_CONFIGURATION_MCP_URL`、`AI_PLATFORM_URL`、`PLATFORM_CONFIRMATION_ISSUER`、`EMERGENCY_WORKBENCH_*`、`EMERGENCY_CONFIRMATION_*`、`AI_WORKBENCH_EMERGENCY_*`）。

## 4. 合并后仍需处理的功能缺口

这些不是架构问题，不阻塞文件合并，但影响"合并后能不能验证通过"：

1. **路由验证未通过**：232 上实测 4 条会话，`aisoc.policy` 通过，`xx.command` / `xx.policy` 均跳过来源核验直接猜平台，`aisoc.emergency` 未测。
2. **XX 来源映射是临时值**：`sourceRef=x-local-check|x-mq-acceptance-asset-01` 未替换。
3. **XX 组合未接真实服务**：两个 `real-tool-contract.json` 仍 `not-configured`。
4. **实例缺 `soc-readonly` 绑定**：源头在 `dsh/managed/web-profile.seed.patch.yml`，当前 9 个服务里没有它，拿不到 `sourceRef`。
5. **223 环境认证不可用**：业务接口全站 503，验证被阻塞。

## 5. 执行顺序

1. 按 2.1 / 2.2 / 2.3 做文件级覆盖与删除；
2. 清理 f610 里对已删文件的残留引用（`patch.yml` 的 `instance-confirmation-config`、`role-tool-matrix.yaml` 的 policy/department/emergency 三组白名单——f237 版本已清理，直接覆盖即可）；
3. 在 `web-profile.seed.patch.yml` 补 `soc-readonly` 绑定，两条 232 直连切 223；
4. 重载实例，确认 `status: current` 且工具目录里出现 `soc-readonly` 的工具；
5. 等 223 认证恢复后跑四种路由验证；
6. 更新 f610 的 `change.yaml`（父版来源、能力标记）与 `decision.md`（写明采纳 f237 架构、未通过的验证项）。
7. `outcome` 由 `inconclusive` 改为实际结论，不因合并动作本身宣称业务通过。

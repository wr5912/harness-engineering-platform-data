## 5.3.1 源/目的资产离线是否影响加策略

**不影响“在防火墙上加 ACL/策略”本身**：

- 防火墙规则是基于源/目的 **IP 或网段**，不要求终端在线；
- 172.16.2.2、172.16.3.2 是资产登记的主 IP，虽然资产状态是 offline，仍可作为规则地址；副 IP 当前 graph 不索引；
- 真正需要在线的是 **FireWall01（172.16.200.10）**，它当前 online。

但要注意两个区别：

1. **加规则/渲染配置**：不要求源/目的主机在线，只要求防火墙在线；
2. **平台的可达性解析/预览/执行后验证**：如果平台走“路径查询”而不是显式指定防火墙，离线主机可能导致解析不到路径或预览失败；这时用 `device_query` 指定 FireWall01 的 IP，绕过源/目的在线依赖。
3. **执行后的连通性验证**：需要源/目的主机在线才能验证策略是否生效；这不影响规则下发。

结论：**源/目的离线不是加策略的阻塞项；FireWall01 在线即可下发。** 但平台侧如果强制要求资产在线，需要单独确认。

## 5.7 结论

1. 多 IP 关系已核实：
   - 172.16.2.3 = asset 3617507 的副 IP；
   - 172.16.3.3 = asset 3617508 的副 IP；
   - 172.16.6.2/6.3 = asset 3617506 的副 IP。
2. 逻辑执行点 **FireWall01 = 172.16.200.10**（asset 3617608，deviceId `dev-360319c8c91f`），当前 **online**。
3. 源/目的资产离线**不影响防火墙加 ACL**；规则基于 IP/网段，不要求终端在线。
4. 平台解析时建议带 `device_query: "172.16.200.10"`，避免走源/目的在线依赖；如果平台强制要求资产在线，再单独确认。
5. 执行后的连通性验证需要源/目的在线；这是验证阶段，不是下发阻塞。
6. **多 IP 解析限制**：SOC graph search 只索引主 IP：
   - `172.16.2.3` → 返回空；
   - `172.16.3.3` → 返回空；
   - `172.16.6.2` → 返回空；
   - 主 IP `172.16.2.2`、`172.16.3.2`、`172.16.6.3` 均能查到。
   因此点到点样例必须用主 IP；如果要按副 IP（2.3/3.3/6.2）解析，需要平台/SOC 增加多 IP 检索能力，当前不支持。

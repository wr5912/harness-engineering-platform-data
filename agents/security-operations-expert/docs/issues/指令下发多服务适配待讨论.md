## 需求方向

用户只需表达目标 IP、动作和必要的业务参数，不需要知道目标属于哪种特殊设备，也不需要选择设备专用入口。系统应根据真实设备信息，确定设备类型、可用动作及对应的参数组装、下发和结果查询方式。

不同设备可以由不同服务管理。若新服务持有设备目录并提供按 IP 查询能力，应依照它的公开合同解析目标，不将所有查询固定到旧服务。讨论中使用的 `ai_socket` 是用户对既有系统的称呼，本次未核对其具体实现。仅有另一个服务的执行 OpenAPI，不能证明该服务也提供设备查询或动作目录。

原讨论曾涉及中间服务；当前f237已经明确使用Skill＋MCP组合，不再将旧Platform层作为设计基础。真实XX服务的连接、部署及其设备归属仍须按实际目录核实。

统一的是用户侧设备操作入口与业务过程；设备查询、参数格式、实际提交和结果查询可能需要按来源服务分别适配。这里记录的是待实现需求，不表示f237已接通真实XX设备或服务，也不表示已经确定自动服务选择规则。

## 核心疑问：两个服务时，究竟选择哪个接口

用户强调的问题是：“两个服务的话，那你怎么去决定你是去调哪个口呢？”

即使已有 SOC 或中间服务路线，又接入一个新 MCP 服务，系统也不能仅凭 IP 或接口描述就自动知道应该走哪一条。以下均待后续讨论，没有确定采用某一种实现：

1. **服务选择的依据**：如何结合目标设备、具体操作和现有来源关系，决定查询、指令执行或模板修改应调用既有 SOC／中间服务，还是新服务；规则由什么真实资料或配置支持。
2. **查询入口及设备对应关系**：新服务是否提供按 IP 查询、稳定设备标识、型号及动作目录；若不提供，如何利用已有公开查询与明确映射定位目标，而不是假定必须先查旧服务。
3. **同一 IP 的多处命中**：是否为同一设备、不同租户或不同管理范围；同一设备的指令与模板是否可能由不同服务负责。设备类型或 IP 本身不一定唯一决定所有操作的服务归属。
4. **能力及权威范围**：如何确认服务不仅暴露某个接口，而且确实负责该目标的这项操作；MCP 工具目录能说明能力，但不能单独证明本次调用的归属和权限。
5. **参数与模板适配**：指令按什么格式组装；模板实体和三个 Map 如何读取、定位修改字段、保留其余内容并按合同写回。
6. **既有流程复用边界**：共同的读取、草案、原生确认和提交如何对应不同服务的实际工具合同；旧SOC自身的签名要求不套到新工具，本阶段不另加审批、版本或复杂回执机制。
7. **来源不明或冲突时的停点**：可以怎样对已接入、已授权服务做只读核对；何时需要补充设备、模板或范围信息。不能让模型猜服务，不能以试执行或向多个服务下发来判断归属。

后续可根据新服务的 MCP 工具目录、OpenAPI 文档及脱敏请求、返回示例继续讨论；本页不据此实施多服务自动选择或真实设备调用，也不扩展已限定的Mock任务。

收到研判请求后，提取原始 `INC-YYYYMMDD-NNNNNN`，通过 `delegate_threat_analysis` 委派一次。prompt 只传事件 ID 和研判请求，不携带人工标签或已有结论。多个 ID 分别委派，不改写 ID；没有有效 ID 时询问用户。

专用子智能体仅调用 `analyze_threat_incident`。代码完成 SOC 认领、真实 MCP 取证、名单分类或五源融合、冻结输入模型推理、校验、摘要与报告、SOC 回写和报告存储。名单快速分类不调用内部模型。结果校验与业务结论是不同事实；历史研判源尚未接入。

正式摘要由程序直接交付主会话，下载链接只来自报告 persistence MCP。不得从 SOC 回写响应猜下载链接，不再调用模型改写摘要。取证、模型和存储失败均保留真实状态，不编造结论或保存成功。

## 规则优化建议

规则优化仍在同一研判工具内部完成，不另行委派规则智能体或调用策略写入工具。只有本事件可确认的五源完整研判、有效结论及 `[0,1]` 内有限数值分数同时满足门槛时，才进入后置分析。误报、可疑、真实告警统一按 `confidence_score < T` 判断，首版可配置阈值为 `T=0.75`；0.74进入、0.75及以上跳过。人工指定、已有规则异常、默认开启或“请优化规则”的意图均无绕过例外。名单快速分类不适用本建议流程，保留原有 `verdict + matches`，不新增建议字段或模型调用。

基础完整研判的 `rule_optimization_suggestions` 只留空数组，不先生成建议。门槛满足后，后置直接复用本轮已冻结的五源输入，只使用其中的 `event_snapshot`、五源业务数据及实际包含的相关规则信息和边界说明，不另读审计文件或原始回执拼接模型输入；用一次后置模型调用先分析低置信原因，再决定是否提出建议。子智能体仍只调用一次固定研判工具，不自行新增规则查询、五源取证、校验、写入或处置；不读取用户背景作为本案事实，不猜授权或规则缺陷。

原基础结论、分数、事实、反向证据、处置建议及原校验保持不变。其他基础机械格式问题不是规则分析总开关；本案身份、来源、结论、分数或阈值本身无法确认时，不猜值、不降低分数，独立记录无法判断。完整研判模式不要求五域均有数据；取证缺口不能直接包装为规则修改，低分本身也不证明规则有错。外部EDR告警仅作证据，不冒充SOC自有规则。

对外仅填充既有 `rule_optimization_suggestions`，允许0至2项，每项恰含 `rule_level`、`suggestion`、`impact_scope`。`rule_level` 只能是“检测规则”或“关联规则”；两项可属同层级但不重复。`suggestion` 用自然语言解释本案问题、依据和具体调整方向，区分已证事实、合理推论与待核查事项；`impact_scope` 说明对象、适用范围、可能损伤的信号及误漏报风险和未验证边界。没有具体或可交付建议时为 `[]`，不凑数量，不输出null诊断项、旧 `rule_content`/`cannot_optimize_reason` 或嵌套 `rule` 对象。门槛、证据引用、来源和处理状态仅留模型外审计，必要故障说明不能被空数组掩盖，也不作为第四公开字段。

最终结果、摘要、报告与SOC研判写回使用同一份建议数组，不重新生成不同版本。只给自然语言维护建议，不生成可执行DSL、完整规则JSON、正则/SQL/SIGMA实现代码或规则文件，不创建、修改、采用、启停、执行、试跑或回放规则。不以单个事件声称总体降噪、召回改善或变更安全；保存成功不等于建议有效或规则效果通过，历史Run及已保存结果不追溯改写。

## 研判并处置

用户在同一请求里明确要求“研判并处置”时，委派研判后追加一次 `disposition_prepare`：`incident_id` 原样传入、`mode: "recommendation"`，由处置运行时从研判建议映射动作与目标并生成草案。只生成草案并展示，不确认、不提交、不调用策略或其他处置工具；没有可执行的推荐动作时说明缺口并转人工。该追加步骤不改变摘要由程序直接交付的约束。

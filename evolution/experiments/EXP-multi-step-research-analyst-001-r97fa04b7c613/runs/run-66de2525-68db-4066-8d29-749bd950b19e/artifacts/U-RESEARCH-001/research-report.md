## 比较结论

## 一、两项目定位差异（同一组问题的横向比较）

| 比较维度 | autoresearch | EvoFlow |
| --- | --- | --- |
| 解决什么任务 | 自主训练研究：把一个小而真实的 LLM 训练装置交给 AI Agent，让它整夜自主做实验，产出实验日志和（期望中）更好的模型 | 长任务业务交付：把长任务交给可协作的 Agent Teams，先澄清规划、再隔离执行、失败可恢复、结果可验收 |
| 任务对象 | 单个研究循环（改代码→短训→看指标→留或弃） | 业务控制平面（对话/Plan/Goal、任务中心、工作流、多 Agent 分工） |
| 人在环路中的位置 | 人不碰训练 Python 文件，只迭代 `program.md` 指令，用「编写研究组织」的方式放大研究进展 | 人在 Plan 阶段可修订计划，关键审批、汇报、可观测与干预贯穿执行 |
| 执行方式 | 单 GPU、单文件、单指标；Agent 只编辑 `train.py`；`prepare.py` 与数据准备/评估工具固定不改 | 桌面安装包或源码自托管；隔离上下文执行工具与沙箱作业；多 Agent 分工与岗位值班 |

## 二、逐来源结论

**autoresearch（karpathy/autoresearch，固定提交 228791fb 的 README 快照）**：它是一个受严格约束的自主研究循环——Agent 只被允许编辑 `train.py` 一个文件，其余(固定常量、数据准备、分词器、dataloader 与评估工具)都在不可修改的 `prepare.py` 中；每次实验固定 5 分钟墙钟，指标为 val_bpb（与词表大小无关，所以不同架构改动可以公平比较）。其最有价值的可迁移点是**约束设计本身**：单一可改文件使改动可复核，固定预算使多次实验可比，单一无关于实现的指标使优化方向可判。它的「人在环路」方式是编写 Markdown 指令文件（README 自述这本质是一种超轻量的 skill）而不是改代码，这与 DSH 现有的 skill / 指令机制同源，可直接沿用。同时它的结论**不可迁移**：固定预算意味着结果只在同一算力平台内部可比，跨平台不可比；要真实训练须自备 NVIDIA GPU、依赖与训练数据，「一夜约 100 次实验」是用法描述而非本平台已完成的训练或已获收益，资料中的安装与调参命令属引用内容，本次未执行。

**EvoFlow（EvovexAI/EvoFlow，固定提交 d921e63 的 README 快照）**：它是一个面向长任务的原生 Agent Runtime 与控制平面，价值在于**长任务生命周期语义**：先澄清与规划（Plan）再执行、长任务后台挂起（Goal）、在隔离上下文中执行工具与沙箱作业、失败可恢复、结果可验收，并以「任务、工具调用与用量可见」加治理套件把可观测与可干预做成一等能力；此外还有多 Agent 分工值班与关键审批汇报。这些是任务编排层需求，与具体产品实现解耦，适合在 DSH 任务机制层按需补齐。

## 三、对当前 Harness 工程平台的借鉴判断

**可以借鉴的任务机制**

- 从 autoresearch 吸收：限定修改面（把 Agent 可写范围收窄到一处）+ 统一预算 + 与实现无关的可比指标，这套组合适用于任何长任务优化循环，不限于机器学习；以及「人类迭代指令文件而非代码」的做法，直接复用 DSH 既有 skill/AGENTS.md 机制即可。
- 从 EvoFlow 吸收：规划先于执行、失败可恢复、长任务可挂起、过程可观测可干预的编排语义，按需补进 DSH 任务机制层。

**不能直接沿用或需谨慎的部分**

- 不照搬 EvoFlow 整个平台。其控制平面（对话/Plan/Goal、任务中心、工作流、应用中心与自动化、资源市场、治理套件、多账号 SSO、IM 渠道、桌面安装与自托管交付链）是完整产品级栈，远超调研助手所需，且与 DSH 现有能力重叠，重复实现性价比低。
- EvoFlow 的许可边界必须保留：PolyForm Noncommercial 1.0.0 为源码可见许可，商用须书面授权，**不是** OSI 开源许可；任何代码、UI 或协议层面的直接复用都须先确认是否落在个人学习、研究、非商业使用范围内，并按 NOTICE 清理第三方组件（含 ZCode Apache-2.0）许可。autoresearch 为 MIT，复用门槛低得多。
- 平台支持不可想当然：autoresearch 当前要求单张 NVIDIA GPU，CPU/MPS 需依赖社区分支或参照父项目 nanochat 并大幅下调词表、序列长度、深度、批大小等超参。

**结论**：两份资料分别提供了「受约束的自主优化循环」和「长任务的规划—恢复—可观测—验收」两类机制性参考。对当前平台，正确做法是借鉴这两类任务机制、优先复用 DSH 既有能力，而不是移植任何外部平台的完整实现或其许可条款。

### 来源 1

资料为固定提交 228791fb 的 README 快照。定位：给 AI Agent 一个小而真实的 LLM 训练装置，让它整夜自主实验——改代码、训练 5 分钟、判断是否变好、保留或丢弃、重复；早上得到实验日志和（期望中）更好的模型；训练代码是 nanochat 的单 GPU 简化实现。人不改训练 Python 文件，而是编写 `program.md` 给 Agent 提供上下文并搭建自主研究组织，README 自述 program.md 本质是「一种超轻量的 skill」。结构上只有三个关键文件：`prepare.py` 固定常量、一次性数据准备（下载数据、训练 BPE 分词器）与运行时工具（dataloader、评估），不修改；`train.py` 是 Agent 唯一编辑的文件，含完整 GPT 模型、优化器（Muon + AdamW）与训练循环；`program.md` 由人类编辑迭代。设计选择：单一可改文件（使 diff 可复核）、固定 5 分钟墙钟预算（不含启动/编译，约 12 次实验/小时、睡觉期间约 100 次；好处是不同改动间可直接比较并能在该预算下找到平台最优模型，代价是与在其他算力平台上的运行结果不可比）、自包含（除 PyTorch 与少量小包外无外部依赖，无分布式训练、无复杂配置，一 GPU 一文件一指标）。指标为 val_bpb（验证位每字节比特，越低越好，与词表大小无关，故架构变更可公平比较）。运行前提：单张 NVIDIA GPU（在 H100 上测试）、Python 3.10+、uv；README 给出 uv 安装、uv sync、uv run prepare.py（一次性约 2 分钟）、uv run train.py（单次约 5 分钟）等步骤，并建议在仓库中启动 Claude/Codex 等并关闭全部权限后按 program.md 开始，这些均属资料引用的操作说明。平台支持：当前要求单张 NVIDIA GPU，CPU/MPS 等原则上可行但会使代码膨胀；小算力平台可参考其列出的社区分支（macOS/Windows/AMD），或参照父项目 nanochat 的 Flash Attention 3 回退、通用设备支持与自动检测等方案；面向更小模型给出的调参方向包括改用低熵数据集（如 TinyStories）、下调 vocab_size、降低 MAX_SEQ_LEN 并相应调整 DEVICE_BATCH_SIZE、下调 EVAL_TOKENS、降低 DEPTH、改用 WINDOW_PATTERN "L"、下调 TOTAL_BATCH_SIZE 等。许可：MIT。

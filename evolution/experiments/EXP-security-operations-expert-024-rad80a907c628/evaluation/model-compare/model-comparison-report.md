两个口径的差异需要说明：平台结算的证据包中子代理 Session 事件不完整，因此**平台口径不含子代理调用**；本报告的逐调用口径来自实例完整日志，含子代理。这也解释了为什么 27B 的逐调用输入（32.7M）远高于平台观测（3.1M）——差额几乎全部来自 625 次子代理调用的累积上下文（29.4M）。

观察：

- **委派结构差异是最大的 token 分水岭**：27B 触发 625 次子代理调用、消耗 29.4M 输入 Token；4B 只有 153 次、1.8M。27B 总输入约为 4B 的 5 倍，但主 Session 单次输入反而更低（上下文被委派分担）。
- **4B 的评审输出膨胀**：judge 输出 70,381 vs 27B 的 23,711（约 3 倍），且 69 次全部不是合法 JSON——大量 token 花在了无效的评审生成上。
- 本地路由无远程费用结算，以上为 Token 用量，不是费用。

## 五、结论

1. **效果**：27B 轮给出了可区分的结果（10 通过 / 17 失败 / 42 无法判定）；4B 轮因评审模型无法产出合法 JSON，69 个用例全部无法判定，**不能据此比较两者被测行为的优劣**。若要得到 4B 的真实效果数字，需要把评审与被测解耦（例如评审固定用 27B 或其他稳定模型）后重跑。
2. **速度**：单次被测响应 4B 明显更快（P50 约 1.9s vs 4.0s），但评审调用更慢且产出无效。
3. **成本（Token）**：27B 通过委派产生 5 倍输入 Token 总量；4B 主调用更多、评审输出膨胀，总输出反而更高（194k vs 168k）。
4. **可比性边界**：两轮评测实现与资产摘要一致、用例与执行参数一致，仅模型与程序仓库提交不同；评测实例的外部 MCP 断连等环境因素对两轮同样存在，失败归因需结合 Run A 报告逐例阅读。

# 00 验收范围与原则

## 1. 验收对象

本工具是 AI 文档工程系统，而不是普通 AI 写作工具：

~~~text
模型
+ 提示词和 Harness
+ 原始材料与知识库
+ 需求和评分解析
+ 证据与事实管理
+ 方案与决策对象
+ 文档编排和导出
+ 规则校验与验证器
+ 权限、审批和审计
+ 评测、回归和发布门禁
~~~

## 2. 两条产品路线

### 投标响应编译器

RFP、补遗、评分办法和组织能力材料，编译为：

- 合规矩阵；
- 评分响应；
- 技术方案；
- 证据包；
- 评审记录；
- 电子提交包。

### 工程设计编译器

设计任务书、现状资料、需求和约束，编译为：

- 场景和目标；
- 架构和视图；
- 方案选项和决策；
- 接口和数据；
- 实施、运维和测试；
- 验收条件和验证矩阵。

两条路线共享材料、需求、证据、版本、评审、发布和审计底座，但不能强行共用同一套章节模板和评价规则。

## 3. 六条核心原则

### 3.1 结果优先于表达

先检查要求是否完成、证据是否充分、输出是否可发布，再检查语言是否漂亮。

### 3.2 证据优先于推断

必须区分已确认事实、原文来源、工具结果、推断、设计假设、待确认事项和建议。

### 3.3 权限优先于便利

模型生成内容不自动获得读取、导出、发布和跨项目访问权限。

### 3.4 受控自动化优先于无边界自治

建议分为建议、半自动、受控自动和高风险受控四级。最终报价、重大承诺、法规结论和高风险发布需要人工审批。

### 3.5 失败必须可见、可停、可恢复

OCR、模型、检索、工具、导出和发布失败都必须有状态、原因、重试、暂停、升级和恢复路径。

### 3.6 改进不能造成关键能力回退

模型、提示词、工具、路由、知识库、模板或规则变化后必须运行关键回归集。

### 3.7 开源复用优先

编辑器、Markdown、Mermaid、表格、差异对照、文件解析、DOCX 生成和发布审计等能力，必须优先检索和评估成熟开源组件。只有在开源组件无法满足证据追踪、权限、审计或交付要求时才自研补齐。选型必须记录版本、许可证、改造范围、安全边界、升级和替换策略。

## 4. 验收层级

~~~text
L0 需求层：需求清晰、可验证、可追踪
L1 功能层：模块按需求工作
L2 场景层：端到端交付流程闭合
L3 质量层：准确性、证据性、一致性、稳定性和性能
L4 治理层：权限、审计、发布、回滚和持续改进
~~~

## 5. 不可作为单独验收依据的内容

- 一次性现场问答；
- 模型自评；
- 只展示生成长文；
- 没有固定输入的录屏；
- 只展示按钮存在；
- 只有截图或效果图而没有可执行 HTML 和可复验状态；
- 没有来源和证据的“专家感”文案。

## 一、今天下午做了什么

### 1.1 排查：两类不同的问题，不要混为一谈

排查了四个会话，结论是失败原因分属两层：

智能体侧（本次已修）：

- `session-a49de173`：用户说"通过 Wazuh EDR 封禁"，模型却选了防火墙动作 `block-ip`，报"目标不属于此动作的合格执行点"，随后没有改正动作，反而用选择面板把用户从 EDR 引到防火墙。
- `session-e6051257`：动作选对了（`host-block-ip`），但把 `preview.online=false` 误判为"需要额外确认门禁"，用相同参数重复调用两次，最后宣称"hard stop at execution gate"。真实原因是设备未通过在线校验。
- 同批次会话里还有一次输出语言漂移：思考摘要与正文全部英文。

SOC 侧（未修，已登记 issue #124）：

- `block-ip` 在 OPNsense（型号 8）渲染失败，缺 `acl-rule-set`、`acl-interface-binding`、`acl-observed-order`，且 `input-fields` 不提供这些字段。
- `policy_change` 的 ADD 需要"插入位置 + 参考规则"，返回 601，但工具 schema 与字段目录都没有该入口。
- Wazuh `host-block-ip` 渲染出的 active-response 中 `command` 与 `dispatch_id` 为空字符串。
- Wazuh 设备 `dispatchCredentialRef` 为 null，`preview.online=false`，且预览不返回原因。

设备侧核查结论：三台 OPNsense 中仅 `dev-b3e6f5ca4031`（172.16.1.10）配置了 `opnsense-api` 下发凭据；Wazuh `dev-39b0a2d19bbf` 无凭据。当前 223 上没有可真实完成封禁下发的目标。

### 1.2 修改：三处行为调整

只改了 `dsh/workspace/.agents/skills/` 下两个 Skill，其余资产未动。

改动一：先按执行对象选动作，不按关键词猜平台

原缺陷：模型先选动作再找设备，导致"EDR 封禁"被当成"防火墙封禁"，失败后又改用户的目标设备。

新规则：用户说通过 Wazuh/EDR 或在受管主机上处置，只能选 `host-block-ip`、`host-unblock-ip`；用户指定防火墙或要求按厂商封堵，只能选 `block-ip`、`unblock-ip`。动作与目标不匹配时先改正动作，不得换设备，也不得用选择面板把用户从 EDR 引到防火墙。

改动二：默认先预览，明确要求才执行

原缺陷：AISOC 两个 Skill 允许"授权完整时直接 apply/execute"，导致用户一提出处置就进入执行位，中间没有草案可看。

新规则：用户没有明确要求下发或执行时，一律用 `preview` 并交付草案；`draft` 仅在明确要求保存草稿时使用；`apply` / `execute` 仅在出现"确认执行""直接下发""立即执行"这类明确表述时使用。第二次执行复用本会话已确认的设备、参数，不重新发现设备、不重查来源、不重跑目录查询；回执与首次草案的关键字段不一致时明确指出差异。

这条与 XX 两个 Skill 的既有做法对齐——那边本来就是"preview 出草案 → 原生确认 → apply"两段式。

改动三：允许修正，但有界，且不得枚举字段名

原缺陷：601 之后模型转向原始预览接口，用 `position`、`insert_before`、`insertBefore`、`insertPosition`、`ruleBefore` 逐个试字段名，连试 8 次全部返回同一错误。

新规则：同一阻塞最多修正两次，每次都须基于新依据（当前 `inputSchema`、`input-fields`、错误点名项或用户补充的新事实），并说明改了什么、依据是什么；不得对同一个值更换字段名反复枚举；两次后仍失败就停止，并分类报告是"缺少具体取值""上游未提供接口"还是"能力不支持"。

附带：明确交付默认使用简体中文，不因内部推理语言改变。

## 三、合并到主线

### 3.1 前提

- 主线资产以 `EXP-security-operations-expert-027-m-reab20c48f610` 的 `candidate/dsh/` 为准，不要以 Git 历史某个提交为准。
- 只合并上述两个 Skill。`xx-device-command`、`xx-policy-template` 已验证无差异，不要覆盖。
- `dsh/managed/`、`dsh/presets/`、`AGENTS.md` 本次未改。压缩包里它们是 f237 现状，若主线对应文件已有更新，**以主线为准**，不要整目录覆盖。

### 3.2 逐处合并

推荐做法：以主线文件为基准，按第二节列出的一处一处改，而不是整文件覆盖。因为主线的第 2、3、5、6、7 条可能各自还有其他改动，整文件覆盖会丢。

合并前先做一次差异确认：

```bash
diff <主线>/policy-configuration/SKILL.md <压缩包解压>/dsh/workspace/.agents/skills/policy-configuration/SKILL.md
diff <主线>/emergency-action/SKILL.md <压缩包解压>/dsh/workspace/.agents/skills/emergency-action/SKILL.md
```

如果主线这两个文件与上面"改动前"的描述一致，差异应当只有本文件第二节列出的六处；若出现更多差异，说明主线另有改动，需人工判断，不要盲合。

### 3.3 冲突判断

- 主线第 6 条（policy-configuration）若已被改成默认 preview，只需核对措辞是否覆盖"执行复用"和"回执比对"，缺则补。
- 主线 emergency-action 第 2 条若已包含动作选择规则，则只补 `preview.online` 那一段。
- "允许修正但有界"整句两处内容相同，若主线已有类似表述但更宽松，直接替换为这句，不要叠加。
- 任何情况下不要删除主线已有的其他约束。

### 3.4 验证

静态检查：

```bash

grep -c "允许修正但有界" <主线>/policy-configuration/SKILL.md <主线>/emergency-action/SKILL.md
grep -c "不得对同一个值更换字段名" <主线>/policy-configuration/SKILL.md <主线>/emergency-action/SKILL.md
```

三组都应至少为 1。

运行验证（需重载实例后开新会话，旧会话不会重新装载 Skill）：
